# HR Vision: готовность инфраструктуры, 04.10.2026

Статус: исследование, не решение о размещении и не выполненная настройка. Проверки серверов были только на чтение. После уточнения границ задачи новые удалённые проверки и дальнейшее исследование backend остановлены. Этот документ сводит уже полученные результаты.

## Вывод

На текущую машину `dsa` нельзя безопасно выкладывать backend с постоянным состоянием: при проверке 04.10.2026 в 07:10:15 UTC (10:10:15 МСК) корневой диск был заполнен на 100%, доступно 0 байт. Публикация статического макета утром состоялась, но проблему заполнения диска не устранила.

На `outreach` есть измеренный запас диска и памяти. Это возможное место для небольшого API после отдельного согласования, а не уже выбранная площадка. Свободные ресурсы сами по себе не подтверждают готовность авторизации, хранения приватных видео, резервного копирования и LiveKit.

Ни серверы, ни сервисы, ни данные, ни конфигурация Caddy в рамках этого исследования не менялись. Очистка, перезапуски и публикация не выполнялись.

## Почему недостаточно разово освободить место

Прочитанные метаданные Docker показали:

- `langfuse-clickhouse-1` unhealthy; его Docker logging driver `json-file`, `Config: {}`. В метаданных этого контейнера нет заданных параметров ротации `max-size`/`max-file`.
- У ClickHouse `HostConfig.Memory=0`, `NanoCpus=0`: явные лимиты памяти и CPU для этого контейнера не заданы.
- Каталог данных ClickHouse занимает 7.7 GiB, каталог его файловых журналов 698 MiB.
- `clickhouse-server.err.log` имеет размер 436 908 032 байта; три сжатых архива `clickhouse-server.log.*.gz` имеют размеры примерно 97–99 MB каждый.
- Системный journal занимает 439 MiB, `/var/log` в целом 687 MiB. Проверенный вывод конфигурации journald не показал явного `SystemMaxUse`; полная политика лимитов всех журналов этим не установлена.
- Помимо ClickHouse unhealthy были Langfuse PostgreSQL, Redis, MinIO, Kaneo и его PostgreSQL, а также приложение исследования стекла Proteus. Причины каждого health check отдельно не исследовались.

Скорость текущего роста файлов и конкретный источник заполнения после утреннего сжатия этим снимком не установлены. Данные не дают права удалять журналы или данные ClickHouse. Для устойчивого размещения нужен отдельно согласованный способ обеспечить свободное место и ограничить дальнейший рост, затем повторная проверка запаса.

Существующий скрипт статической публикации требует место под архив и новый выпуск плюс не менее 512 MiB резерва. Backend, база, WAL, загрузки и резервные копии требуют собственного бюджета сверх этого минимума. При 0 байт доступного места не следует запускать миграции, приём файлов или новую публикацию.

У сервиса `MemoryMax=300 MiB`, пользователь `nikita`. Прочитаны имена переменных окружения и пути конфигурации, но не значения секретов и не записи кандидатов. Наличие этих маршрутов подтверждает полезную отправную точку для панели и видео, но не доказывает нужную ролевую авторизацию, приватность видео отказа, офферы, серверную модель нового продукта или пригодность исходника для прямого переноса. Дальнейший аудит кода остановлен по границам задачи.

### Интервью на outreach

На outreach уже работают:

- `oasis-backend.service`, описание OASIS interview backend, `127.0.0.1:8300`, рабочая папка `/opt/oasis/src/backend`, `MemoryHigh=900 MiB`, `MemoryMax=1200 MiB`;

## Варианты, требующие решения

1. **Backend на dsa после устранения инфраструктурного инцидента.** Сохраняет текущую публичную площадку и простой localhost upstream, но зависит от восстановления и ограничения роста общего диска. Сейчас заблокирован.
2. **Backend на outreach, HTTPS-вход через существующий dsa.** Есть измеренный запас ресурсов, однако это новое размещение на общей машине. Потребуется отдельный закрытый маршрут между VM. Публичный вход всё равно зависит от dsa, поэтому это не полная изоляция от его инцидента.
3. **Отдельная площадка приложения/RTC.** Даёт отдельный бюджет ресурсов и эксплуатационные границы, но требует согласования инфраструктуры, затрат и секретов. Ничего не создано.

Выбор между ними не сделан. Разворачивать новый RTC-сервер или обработку видео на dsa при измеренной нагрузке и заполненном диске нельзя считать готовым вариантом.

## Предлагаемый набор конфигурации для согласования

Ни один перечисленный ниже файл или объект не создан. Имена и параметры являются проектом минимального размещения, а не утверждённой реализацией.

| Объект | Предлагаемое назначение |
|---|---|
| `app-server/` в репозитории | Отдельный Node backend с серверной проверкой пользователя, роли и доступа к конкретной записи |
| Отдельная сборка приложения | Клиентский кабинет под `/app/`, независимый от Storybook; действующие истории сохраняются |
| `deploy/hr-vision.service` | Описание службы с отдельным системным пользователем, localhost bind, обязательным `MemoryMax`, контролируемым restart и выводом в journald |
| `/etc/hr-vision/env` | Серверные настройки и секреты, права 600; не входит в выпуск и не отдаётся Caddy |
| `/var/lib/hr-vision/` | Состояние вне каталога релиза: БД, журнал бизнес-событий и метаданные файлов; доступ только пользователю службы |
| Приватное хранилище видео | Отдельное от статического `/srv/hr-vision/current`; доступ проверяется сервером; ограничения размера, срока хранения и общего объёма требуют согласования |
| Дополнение HR site block Caddy | Маршрут API на приватный backend и маршрут `/app/`; существующий общий Caddyfile нельзя заменять файлом одного сервиса |
| Отдельный deploy и откат | Локальная сборка, контроль свободного места, проверка целостности, атомарная смена выпуска и совместимость миграций с откатом |
| Резервное копирование | База и метаданные вне машины приложения; согласованные срок хранения и проверка восстановления |

Порт `127.0.0.1:3027` отсутствовал в обоих полученных списках TCP listeners и может рассматриваться как кандидат для нового Node API. Это не резервирование: непосредственно перед согласованной установкой занятость нужно проверить снова. Публичный доступ к этому порту не нужен.

Для минимального API можно рассмотреть начальный `MemoryMax=512M`, но это проектное ограничение, а не результат нагрузочного теста. Ресурсоёмкая обработка/перекодирование видео не должна без оценки попадать в тот же процесс. Выбор SQLite или отдельной PostgreSQL-базы также не сделан: наличие чужой БД на машине не является разрешением использовать её данные или учётные записи.

## Что ещё не подтверждено

- Выбранная площадка и разрешение на изменения её конфигурации.
- Восстановленный запас диска dsa и защита от повторного заполнения.
- Продакшен-авторизация, роли менеджера/кандидата и контроль доступа к каждой записи.
- Выбранное приватное хранилище видео, лимиты и резервное копирование.
- Рабочий LiveKit project/server и серверные credentials; создание встреч и доступ в комнаты из кабинета.
- Модель оффера, права изменения и подтверждения, сохранение версий и действий на сервере.
- Сквозная проверка между независимыми браузерными сессиями, проверка запрета чужого доступа и восстановление после перезапуска.

До подтверждения этих пунктов опубликованный интерфейс остаётся статическим прототипом. Этот отчёт не объявляет продукт готовым к работе с реальными кандидатами.
