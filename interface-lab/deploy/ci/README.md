# Две ветки и автоматическая выкладка

| Ветка | Сборка | Адрес |
| --- | --- | --- |
| `main` | Работающий сервис, три входа работодателя/кандидата, API | https://hr-vision.158-160-179-53.sslip.io/ |
| `codex/mockups` | Галерея пяти меню, варианты подборки, предыдущие экраны, CJM/XPM | https://hr-vision-lab.158-160-179-53.sslip.io/ |

Любой push в эти две ветки запускает `Deploy HR Vision`, включая изменения документации. После успешных проверок обновляется только адрес своей ветки. Изменения в других ветках и чужих forks ничего не выкладывают. Перенос выбранного интерфейса из макетов в сервис делают отдельным изменением `main`; автоматического слияния нет.

`interface-lab/build-target.json` различается по веткам. Конфигурация Storybook исключает макеты из сборки сервиса и подключённый продукт из сборки макетов. Общие исходники остаются доступными для переиспользования. CI сверяет target с веткой; попытка слить неверный target останавливает выпуск. Старые ссылки на макеты на основном домене перенаправляются на лабораторию с сохранением query-параметров, включая `menu=sidebar`.

## Как изменить

1. Выбрать нужную ветку. Для работающего процесса это `main`, для интерфейсных альтернатив это `codex/mockups`.
2. Изменить файлы, сделать commit и push (или принять pull request в нужную ветку).
3. Открыть [Actions](https://github.com/NPtow/hr-vision/actions/workflows/deploy.yml). Зелёный `deploy` означает, что публичный `deployment.json` совпал с коммитом.

Публичный репозиторий доступен для чтения всем. Для прямого push нужен доступ Write; без него можно прислать pull request из своего fork.

Повторный выпуск того же коммита: Re-run all jobs в Actions или `gh workflow run deploy.yml --ref main` / `--ref codex/mockups`. Изменение только сохранённых на компьютере файлов сайт не обновляет. Проверки занимают время; неуспешная сборка оставляет предыдущий сайт доступным.

## Устройство

Сборка выполняется на GitHub-hosted runner, а не на сервере приложения. Node 24, `npm ci` из lock-файла, типизация, разбор транскрипта, unit/HTTP-тесты на отдельной временной SQLite, проверки приёмника, затем Storybook и ограниченный release-архив.

В отдельной deploy job доступен ключ только для её GitHub Environment: `service` разрешён лишь для `main`, `mockups` лишь для `codex/mockups`. `HR_DEPLOY_KEY` и `HR_DEPLOY_KNOWN_HOSTS` хранятся в environment secrets; `HR_DEPLOY_HOST` в environment variables. PR-код и npm install не получают deploy key. Все Actions закреплены по SHA.

SSH входит на dsa через отдельного `hr-vision-relay`. Каждый ключ принудительно запускает только передачу архива своего target на outreach. Ни shell, ни port forwarding, ни sudo на dsa через этот ключ недоступны. Внутренний ключ реле тоже ограничен одной командой приёмника своего target. Основной ключ администратора и Daily API key в GitHub не передаются.

`receiver.py` устанавливается администратором как root-owned `/usr/local/libexec/hr-vision-ci/receiver.py`; входная команда `/usr/local/sbin/hr-vision-receive`. Приёмник проверяет размер архива, запрет symlink/path traversal, список файлов и SHA-256, target/branch, актуальный SHA ветки и состав историй. Он не выполняет скрипты из архива. Инфраструктурные изменения самого приёмника/SSH/Caddy требуют отдельной установки администратором; обычные UI и Python API обновляются автоматически.

## Выпуск исправлений бэкенда звонков 20 октября

Перед первым выпуском отдельно установите проверенный receiver из этого
коммита. Runtime добавляет `call_cleanup.py` и `media_runtime.py`.
После создания `cp_call_cleanup` старые runtime без worker не допускаются
к запуску даже при пустой очереди: триггер продолжает создавать задачи
закрытия при отмене встреч. Используйте совместимый forward recovery;
не удаляйте очередь или триггер ради отката. Защита живых встреч и резервная
копия SQLite перед миграцией остаются обязательными.

## Выпуск HH-рассылки

Перед первым выпуском HH-рассылки нужно отдельно установить обновлённый приёмник: прежний allowlist отклонит новые Python-модули. В API-архив входят `candidate_booking.py`, `hh_outreach.py`, `hh_outreach_routes.py`, `hh_outreach_worker.py` и пакет `hh_browser` (`__init__.py`, `adapter.py`, `store.py`, `bridge.py`). Они принимаются только вместе с полным действующим API. Все прежние полные наборы сохранены в `RUNTIME_LAYOUTS`, поэтому откат не требует добавлять новые модули в старую версию. Изменение вложенного файла пакета вызывает backup и перезапуск API так же, как изменение `app.py`.

`hh_browser/integration.py`, профиль Chromium, selector profile, окружение и ключи не входят в релиз API. Настройка bridge в существующем `hh-daily` и вход в серверный HH-браузер выполняются отдельно; выкладка API сама по себе не подтверждает готовность отправки. HTTP-клиент bridge использует стандартную библиотеку Python; запуск нового браузера и установка Playwright в процесс API не требуются.

В сервисной сборке остаются ровно три истории: `start`, `manager`, `candidate`. Операторская рассылка открывается внутри `manager?workspace=outreach`, отдельной четвёртой истории нет. Проверка `python3 -m unittest -v test_receiver` сверяет реальный JS-упаковщик с приёмником, запрет неполных наборов, откат, вложенные файлы и замыкание локальных Python-импортов, включая относительные импорты внутри пакета.

## Сохранность работающего процесса

Для выпуска общего календаря приёмник дополнен `interview_scheduler.py`.
Перед первым таким выпуском установите обновлённый `receiver.py` по указанному выше пути.
Полный предыдущий состав API сохранён в `PRE_POOLED_RUNTIME`, поэтому откат остаётся доступен.

- Состояние `/var/lib/hr-vision-api/` и `/etc/hr-vision/api.env` находятся вне релизов и не заменяются.
- Макеты публикуются в `/srv/hr-vision-mockups/`, их hostname не проксирует API и не получает cookie рабочего сервиса.
- Работающий UI публикуется в `/srv/hr-vision/`. API обновляется в `/opt/hr-vision-api/`, только если изменились файлы Python; изменение UI не перезапускает API.
- При изменении API перед выпуском проверяется отсутствие активного звонка и сохраняется отдельная SQLite backup. Во время звонка выпуск останавливается; после встречи его можно повторить в Actions.
- Новый релиз активируется симлинком. Сбой origin health/revision check возвращает предыдущие указатели UI/API только после проверки совместимости предыдущего API с текущей очередью (см. ниже); состояние базы автоматически назад не откатывается.
- `current` и `previous` сохраняют версии приложения. Наличие `previous` не гарантирует совместимости с новыми данными. Старые релизы автоматически не удаляются.
- Публичный `/deployment.json` показывает ветку и точный SHA. Секретов и пользовательских данных в нём нет.

Старые ручные `deploy-yc.sh` / `deploy-api-yc.sh` теперь запускают этот же workflow. Они не публикуют незакоммиченные файлы и не обходят GitHub.

## Откат после выпуска lifecycle-уведомлений

До выпуска `meeting_notifications.py` установите reviewed receiver с проверкой
`guard_outbox_runtime`. Прежние полные архивы по-прежнему принимаются, но их
активация разрешена только при совместимом состоянии `cn_outbox`.

При каждом переключении API, включая автоматический fallback после ошибки
старта или health check, приёмник синхронно останавливает `hr-vision-api`.
HTTP-производители и общий worker должны работать только в control group этого
unit; отдельный ручной worker/писатель базы во время выкладки не поддерживается.
Под существующими deploy locks приёмник открывает существующую SQLite в `mode=rw`,
берёт `BEGIN IMMEDIATE`, проверяет очередь и меняет указатель. Блокировка базы
снимается перед запуском API. Таким образом, учитывается и последняя транзакция,
завершившаяся во время остановки; проверка до запуска новой версии не заменяет
проверку перед fallback. UI-only и mockups не останавливают API.

Любая строка `meeting.completed` или payload с lifecycle-маркером запрещает
запуск runtime без `meeting_notifications.py`: это относится и к кандидату,
и к работодателю, ко всем статусам, включая доставленные/terminal строки,
которые прежний retry-код мог бы повторно активировать. Очередь, получатели,
попытки и статусы не изменяются. Пустая очередь, обычные прежние строки и
историческая схема до появления outbox/`payload_json` допускают прежний layout.
Неполный runtime, некорректный payload/схема, недоступная или занятая база
останавливают небезопасное переключение. Это проверка добавленного lifecycle
контракта, а не гарантия всех исторических миграций приложения.

Если явный выпуск старого runtime отклонён, приёмник пытается безопасно вернуть
текущий совместимый API. Если новая версия успела сохранить lifecycle-строки,
а затем не прошла health check, автоматический откат к старой версии запрещён:
после успешной остановки API остаётся остановленным, указатель API сохраняется
на новой версии, указатель UI остаётся в достигнутом состоянии. Команда выдаёт
ошибку и указание на совместимое forward recovery; это не успешная выкладка.
При ошибке самой команды stop состояние unit нужно проверить отдельно.

Практическое восстановление: проверить состояние unit и оба `current`, устранить
причину неуспешного запуска/health check и выпустить проверенный полный runtime
с поддержкой lifecycle через тот же приёмник. Совместимая предыдущая версия с
`meeting_notifications.py` может использоваться для fallback. Не переключайте
API вручную на старый `previous`, не удаляйте строки и не восстанавливайте старую
SQLite ради обхода проверки: это потеряет новые события/действия пользователей.
Доставка всех lifecycle-строк сама по себе не открывает откат — записи остаются
в базе. Если проверка базы недоступна, сначала восстановите её доступность.

## Отдельная демка заметок на встрече

`manager&demo=meeting-notes` использует обычную авторизацию работодателя и отдельные
таблицы `ml_*`. В сервисе по-прежнему три истории; новая демка не создаёт кандидатов
и не меняет этапы подбора. В API-архив добавлен `meeting_lab.py`. Перед первым выпуском
нужен обновлённый root-owned receiver. Прежний полный набор API остаётся допустимым
в `PRE_MEETING_LAB_RUNTIME`. Он поддерживает lifecycle-очередь, поэтому новый модуль
не запрещает откат к предыдущему совместимому runtime. Lab-данные при этом сохраняются.
Проверка активных звонков учитывает также `ml_sessions.status='live'`.

## ClickStack observability

Before deploying instrumentation, install the reviewed receiver from this commit:
`observability.py` is a new required runtime member. `PRE_OBSERVABILITY_RUNTIME`
preserves the previous full layout for guarded rollback. Set `HR_OTEL_ENDPOINT`
only after the loopback collector is healthy; the default is disabled. See
`../observability/README.md` for the outreach stack, privacy and capacity limits.

## Календарь кандидата

Перед первым выпуском установить обновлённый `receiver.py`: пакет включает
`candidate_availability.py`. Недельные правила и исключения по датам хранятся
в JSON профиля; доступные UTC-интервалы вычисляются на ближайшие 28 дней при чтении.
Существующие интервалы сохраняются отдельно от вычисленного расписания.
Часовой пояс календаря влияет на отображение, а каждое правило хранит свой пояс.
Назначенные встречи не меняются при редактировании доступности.

`PRE_CANDIDATE_CALENDAR_RUNTIME` сохраняет предыдущий полный состав. После сохранения
правил, исключений или часового пояса откат на API без этого модуля запрещён:
старый обработчик профиля потерял бы эти поля при очередном редактировании.
