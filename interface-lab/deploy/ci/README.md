# Две ветки и автоматическая выкладка

| Ветка | Сборка | Адрес |
| --- | --- | --- |
| `main` | Работающий сервис, три входа работодателя/кандидата, API | https://hr-vision.158-160-179-53.sslip.io/ |
| `codex/mockups` | Галерея пяти меню, варианты подборки, предыдущие экраны, CJM/XPM | https://hr-vision-lab.158-160-179-53.sslip.io/ |

Любой push в эти две ветки запускает `Deploy HR Vision`, включая изменения документации. После успешных проверок обновляется только адрес своей ветки. Изменения в других ветках и чужих forks ничего не выкладывают. Перенос выбранного интерфейса из макетов в сервис делают отдельным изменением `main`; автоматического слияния нет.

`interface-lab/build-target.json` различается по веткам. Конфигурация Storybook исключает макеты из сборки сервиса и подключённый продукт из сборки макетов. Общие исходники остаются доступными для переиспользования. CI сверяет target с веткой; попытка слить неверный target останавливает выпуск. Старые ссылки на макеты на основном домене перенаправляются на лабораторию с сохранением query-параметров, включая `menu=sidebar`.

## Как изменить

1. Выбрать нужную ветку. Для работающего процесса это `main`, для интерфейсных альтернатив это `codex/mockups`.
2. Изменить файлы, сделать commit и push (или принять pull request в нужную ветку).
3. Открыть [Actions](https://github.com/NPtow/hr-vision/actions/workflows/deploy.yml). Зелёный `deploy` означает, что публичный `deployment.json` совпал с коммитом.

Публичный репозиторий доступен для чтения всем. Для прямого push нужен доступ Write; без него можно прислать pull request из своего fork.

Повторный выпуск того же коммита: Re-run all jobs в Actions или `gh workflow run deploy.yml --ref main` / `--ref codex/mockups`. Изменение только сохранённых на компьютере файлов сайт не обновляет. Проверки занимают время; неуспешная сборка оставляет предыдущий сайт доступным.

## Устройство

Сборка выполняется на GitHub-hosted runner, а не на сервере приложения. Node 24, `npm ci` из lock-файла, типизация, разбор транскрипта, unit/HTTP-тесты на отдельной временной SQLite, проверки приёмника, затем Storybook и ограниченный release-архив.

В отдельной deploy job доступен ключ только для её GitHub Environment: `service` разрешён лишь для `main`, `mockups` лишь для `codex/mockups`. `HR_DEPLOY_KEY` и `HR_DEPLOY_KNOWN_HOSTS` хранятся в environment secrets; `HR_DEPLOY_HOST` в environment variables. PR-код и npm install не получают deploy key. Все Actions закреплены по SHA.

SSH входит на dsa через отдельного `hr-vision-relay`. Каждый ключ принудительно запускает только передачу архива своего target на outreach. Ни shell, ни port forwarding, ни sudo на dsa через этот ключ недоступны. Внутренний ключ реле тоже ограничен одной командой приёмника своего target. Основной ключ администратора и Daily API key в GitHub не передаются.

`receiver.py` устанавливается администратором как root-owned `/usr/local/libexec/hr-vision-ci/receiver.py`; входная команда `/usr/local/sbin/hr-vision-receive`. Приёмник проверяет размер архива, запрет symlink/path traversal, список файлов и SHA-256, target/branch, актуальный SHA ветки и состав историй. Он не выполняет скрипты из архива. Инфраструктурные изменения самого приёмника/SSH/Caddy требуют отдельной установки администратором; обычные UI и Python API обновляются автоматически.

## Сохранность работающего процесса

- Состояние `/var/lib/hr-vision-api/` и `/etc/hr-vision/api.env` находятся вне релизов и не заменяются.
- Макеты публикуются в `/srv/hr-vision-mockups/`, их hostname не проксирует API и не получает cookie рабочего сервиса.
- Работающий UI публикуется в `/srv/hr-vision/`. API обновляется в `/opt/hr-vision-api/`, только если изменились файлы Python; изменение UI не перезапускает API.
- При изменении API перед выпуском проверяется отсутствие активного звонка и сохраняется отдельная SQLite backup. Во время звонка выпуск останавливается; после встречи его можно повторить в Actions.
- Новый релиз активируется симлинком. Сбой origin health/revision check возвращает предыдущие указатели UI/API; состояние базы автоматически назад не откатывается.
- `current` и `previous` позволяют откатить приложение. Старые релизы автоматически не удаляются.
- Публичный `/deployment.json` показывает ветку и точный SHA. Секретов и пользовательских данных в нём нет.

Старые ручные `deploy-yc.sh` / `deploy-api-yc.sh` теперь запускают этот же workflow. Они не публикуют незакоммиченные файлы и не обходят GitHub.
