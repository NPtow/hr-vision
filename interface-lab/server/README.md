# Связанный тест HR Vision

Публичная статика и API размещены на outreach. API: `hr-vision-api`, loopback 8391, проксируется только отдельным `hr-vision-web` (8381); TLS вход остаётся на dsa. Сборка UI выполняется в GitHub Actions, просмотр/проверка только по публичному HTTPS. Локальный web-сервер не нужен.

## Импорт вакансии, 13.10.2026

`screen=create-vacancy` открывает полноценную страницу внутри кабинета работодателя.
Регистрация и переход с корпоративного сайта сохраняют intent и исходный бриф.
`POST /api/hr/employer/vacancies/import` требует сессию работодателя; возвращает
редактируемые поля, источник, предупреждения и `importId`. Вакансию не создаёт.
Обычный `POST /employer/vacancies` сохраняет проверенные пользователем значения в
канонические `cp_vacancies`; provenance привязывается только из того же workspace.
Структурированные `details` сохраняют место, занятость, график, зарплату,
обязанности, требования, опыт и условия. Кандидатская проекция включает эти поля
в существующее описание без изменения сохранённого черновика и интерфейса.

Источники: текст до 24 000 символов; PDF, DOCX, TXT, MD, CSV, RTF, DOC, ODT,
PNG, JPG и WEBP до 5 МиБ; публичная HTTPS-ссылка на одну вакансию. Изображения и
сканы читаются локальным OCR. Обрабатывается максимум 50 текстовых страниц PDF
или 6 страниц скана, с отдельным ограниченным процессом (35 секунд).
Установить на API-хосте: `poppler-utils tesseract-ocr tesseract-ocr-eng
tesseract-ocr-rus antiword python3-pil`. Скрипты и макросы не исполняются.
Ссылки проверяются с закреплением публичного DNS-адреса на каждом редиректе;
доступ к частным адресам, metadata endpoints и страницам за авторизацией закрыт.
Если источник недоступен или не содержит одной вакансии, UI предлагает файл,
текст или ручное заполнение. Подключение аккаунта ATS для этого не требуется.

Разбор использует текущий серверный CPA через `HR_LLM_BASE_URL`, `HR_LLM_API_KEY`
и `HR_LLM_MODEL` в закрытом `/etc/hr-vision/api.env`. Никаких ключей во фронтенде.
Prompt pack `vacancy.extract-facts`, версия `2026-10-13.3`, находится в
`vacancy_import.py` под Git. Роль — только extractor: strict JSON Schema,
выдержки из ограниченных chunks, проверка точных цитат/значений, один повтор при
нарушении схемы или evidence. Нет генерации недостающих условий или fallback-модели.
Известные инструкции из источника отсеиваются до prompt; они никогда не попадают
в system message. Извлечение не гарантирует полноту: пользователь проверяет поля.

Ограничения на аккаунт в UTC-сутки: 30 попыток и 800 000 зарезервированных токенов
по консервативной верхней границе, включая единственный retry. Timeout провайдера
45 секунд, output 6000 токенов; browser timeout 150 секунд. SQLite хранит usage
отдельно от idempotency cache, lease не даёт старому worker перезаписать новый.
Для URL cache обновляется раз в час. Исходные файлы удаляются после извлечения;
приватный preview и подтверждающие цитаты очищаются через 30 дней при следующем
импорте. Metadata содержит prompt/schema hashes, pack/model, usage, latency и
retries; HTTP-логи не содержат файлов, prompt, ключей или ответов провайдера.

## Автозаполнение кандидата из CV

Загрузка CV в кабинете кандидата и подготовка кандидата рекрутером используют
`HR_CV_MODEL=gpt-6.1-sol`. База и ключ наследуются из `HR_LLM_BASE_URL` /
`HR_LLM_API_KEY`; отдельные `HR_CV_LLM_BASE_URL` / `HR_CV_LLM_API_KEY` необязательны.
Модель импорта вакансий не меняется. При отсутствии настройки загрузка возвращает
ошибку, не подменяет генерацию локальным шаблоном.

Prompt pack `candidate_resume_prompts.py`, версия `2026-10-14.1`:
1. `cv-extractor`: strict Structured Output, все поля заданы в JSON Schema;
   неизвестные значения `null`, каждый факт имеет точную цитату и ID фрагмента.
2. `cv-writer`: короткое «О себе» только из проверенных цитат об опыте.
3. `cv-judge`: отдельный запрос проверяет поля и каждое утверждение черновика.

Транспорт, schema validation, один повтор неверного ответа, фиксированные лимиты
и отсутствие инструментов находятся в `structured_model.py`. Чистый текст CV
очищается от известных инструкций до фрагментации. Файл/его название не отправляются
модели, только ограниченные фрагменты текста. Исходный CV остаётся в приватном
`cp_resumes`; цитаты и результаты стадий хранятся в приватных `cp_resume_*` таблицах
для повторов, удаляются через 30 дней при следующем разборе. В метриках только
hashes, model/version, usage, latency и retries. Содержимое CV не пишется в логи.

Лимиты: 24 000 символов источника; 65 000 UTF-8 байт входа запроса (консервативная
верхняя граница токенов), 3 000 выходных токенов, 45 секунд на запрос / 150 на весь
разбор. В сутки на аккаунт максимум 1 000 000 зарезервированных токенов, на запуск
350 000, включая неудачные запросы. Повтор того же CV использует сохранённые стадии.
Новый файл, смена сессии или истёкший lease не позволяют применить старый ответ.
До завершения проверки форма остаётся на «Разбираем резюме…»; неудача сохраняет
прежний профиль. Зарплата, район, занятость и срок выхода без прямого источника
остаются вопросами кандидату. Его правки во время запроса сохраняются.

Перед первым выпуском установить обновлённый deployment receiver с полным набором
трёх новых модулей. Предыдущие runtime layouts сохранены для отката. Добавить только
`HR_CV_MODEL` в защищённый environment, не менять `HR_LLM_MODEL` работодателя.

Проверки: `python3 -m unittest -v test_vacancy_import test_vacancy_sources`.
Они включают strict-output/injection/недостаточные данные, зарплату и отрицания,
границы доступа, лимиты, session expiry, cache/lease и вредоносные файлы/SSRF.
Обоснование структуры: [исследование ATS и OpenAlex](../../planning/production-launch-2026-10-12/vacancy-import-research.md).

## Telegram-бот, 13.10.2026

`/start` показывает публичный выбор «Я кандидат» / «Я работодатель» и ссылку
на соответствующий кабинет. Выбор роли не создаёт аккаунт и не меняет привязку.
Одноразовый `/start <token>` сохраняет существующую привязку кандидата;
`/vacancies`, `/meetings`, `/status`, `/settings` работают с каноническими `cp_*`.

На outreach прямое подключение Telegram к webhook и прямой исходящий Bot API
дали timeout. Для этого хоста используется polling через **существующий** Xray
на `127.0.0.1:10808`, только в Telegram transport. Закрытое
`/etc/hr-vision/api.env` (root,0600) содержит token/username и:

```dotenv
HR_NOTIFICATIONS_ENABLED=1
HR_TELEGRAM_POLLING=1
HR_TELEGRAM_PROXY_URL=socks5h://127.0.0.1:10808
```

`HR_TELEGRAM_PROXY_URL` допускает только loopback SOCKS5h. Адаптер вызывает
существующий `/usr/bin/curl`: URL с токеном и JSON передаются через stdin,
ответ ограничен размером/таймаутом, ошибки не содержат URL или тела провайдера.
Глобальные `HTTP_PROXY`/`HTTPS_PROXY`, Xray и остальные интеграции не меняются.
Без этой переменной остаётся прежний прямой urllib transport.

Получение обновлений должно быть одно: webhook **либо** polling. Перед переходом
на polling оператор удаляет webhook методом `deleteWebhook` с
`drop_pending_updates=false`, сохраняя входящие события; затем API читает
обновлённое окружение при согласованном перезапуске с проверкой активных звонков
и резервной копией. Не запускать отдельный `candidate_notifications.py --loop`
рядом с API: интерактивный handler подключён к единственному daemon в app.py.
После polling обновления ответы сразу отправляются тем же worker.

Проверять нужно не только health: наличие processed updates, свежий outbox
`delivered` с provider_ref, состояние polling offset и фактический ответ человеку.
Старые disabled события не активируются автоматически. `getWebhookInfo` с пустым
URL подтверждает отсутствие webhook, но сам по себе не доказывает работу polling.
Нельзя печатать токены, chat IDs или полный payload для эксплуатационной проверки.

## Состояние и доступ

### Письмо назначенному рекрутеру

Оба входа кандидата (свой кабинет и персональная HH-ссылка бронирования)
завершаются в `CandidatePortal.book`. В той же транзакции `enqueue_booking`
создаёт одно email-событие на интервью в `rn_outbox`. Получатель определяется
по `cp_recruiter_slot_owners.recruiter_id → rc_accounts.email`, а не по имени
рекрутера или данным кандидата. HR Vision создаёт эти аккаунты, поэтому
рекрутеру не нужно отдельно подключать или подтверждать почту для письма о записи.
Письмо содержит кандидата, дату, время МСК, длительность и ссылку на кабинет.

Для реальной отправки в закрытом `/etc/hr-vision/api.env` нужны
`HR_NOTIFICATIONS_ENABLED=1`, `HR_SMTP_HOST`, `HR_SMTP_FROM` и согласованные
`HR_SMTP_PORT`, `HR_SMTP_SECURITY` (`ssl` или `starttls`),
`HR_SMTP_USER`, `HR_SMTP_PASSWORD`. Значения доступа в репозиторий не помещать.
Без SMTP событие имеет статус `disabled`, а не успешной доставки.
Worker стартует вместе с API; отдельный worker запускать не нужно.
Старые `disabled`/`unverified` события автоматически не переотправляются.
Повторное бронирование не дублирует событие, неопределённый результат SMTP
не повторяется автоматически, отменённые и прошедшие встречи не отправляются.
`delivered` означает принятие SMTP-сервером; попадание в почтовый ящик
проверяется отдельно контрольным письмом после настройки отправителя.

SQLite `/var/lib/hr-vision-api/journey.sqlite3`, режим WAL, все команды под `BEGIN IMMEDIATE`. Перезапуск приложения/выкладка не сбрасывает прогресс. Права процесса `hr-vision`, MemoryMax 256M. Выпуски `/opt/hr-vision-api/releases/`, указатель `current`.

Общий вход: story `hr-vision-product--start`. При первом открытии приватной ссылки `#team=…` сервер запоминает доступ на 30 дней в подписанной Secure/HttpOnly/SameSite cookie; после проверки ключ убирается из адресной строки. Повторный вход по обычному адресу и в новой вкладке показывает готовые аккаунты выбранного подбора без поля для кода. Старые открытые сессии мигрируют автоматически. Без приглашения или сохранённого доступа новый браузер видит понятное сообщение, персональные данные закрыты. Авторизованная кнопка «Скопировать общий вход» получает полную ссылку через API.

Сам HTML/JS ключа не содержит. Ключ хранится в `/etc/hr-vision/api.env` (root, 600), параметр `HR_TEAM_KEY`; его ротация отзывает cookie доступа. Это доступ команды к тестовым аккаунтам выбранного подбора, не production-авторизация реальных кандидатов. API сессии выбирают роль на сервере, токены сохраняются отдельно в каждой вкладке. Cookie разрешает только выбор аккаунта; чтение и изменение состояния по-прежнему требуют сессию выбранной роли. Фидбек работодателя скрыт от кандидатов; черновик оффера также скрыт.

Кандидат принимается вручную или режимом auto, но встреча всегда требует ручного подтверждения. Слот 30 минут; pending/confirmed/live занимают время кандидата и работодателя. Повторный выбор старого времени возвращает 409. Команды содержат generation, чтобы вкладка до сброса не перезаписала новый тест. Встречи/чаты раздельные по кандидатам. Один отправленный оффер; принятие закрывает подбор. Изменённые условия увеличивают версию: ответ на старую версию отклоняется.

## Фидбек по фактическому интервью

`meeting.transcript` сохраняет финальные реплики работодателя в его активной встрече. При `meeting.finish` фиксируется анкета из реально заданных вопросов. `POST /api/hr/feedback/questions` доступен только работодателю после завершения: использует уже замороженную анкету или получает готовый Daily VTT вне блокировки общей базы. Нет транскрипта/нет распознанных вопросов: status processing/missing/unavailable, без выдуманных вопросов. `feedback.questions` позволяет явно указать свои заданные вопросы. `feedback.draft` и `feedback` требуют текущие meetingId/questionnaireId; отправка требует ответ на каждый вопрос. Анкета, черновик и фидбек скрыты от кандидата. Старые сохранённые отзывы поддерживаются только для чтения.

Извлечение детерминированное, без LLM. Это не автоматическая оценка кандидата. Вся синхронизация остаётся в текущем серверном тесте; реальные Telegram-уведомления и продуктивная аутентификация не добавлены. ## Подключение исходной панели ДСА

`GET /api/hr/dsa-candidates` доступен только с сессией работодателя. Сервер читает `https://kabinet.158-160-179-53.sslip.io/api/candidates`, кеширует результат на минуту в памяти и переводит явно разрешённые поля в DTO. Данные кандидатов не входят в JS-сборку и Git. Ошибка источника показывается явно. Сетевой запрос выполняется вне блокировки общей SQLite.

У работодателя есть отдельная задача «ДСА Инжиниринг». Видео воспроизводится через уже существующий `/api/video/{id}` исходного кабинета; сервер источника обновляет ссылку Яндекс Диска. Короткая версия использует исходные границы фрагментов; полная версия показывает исходные главы. Описания глав и прямые цитаты различаются. Профиль, резюме, оценка рекрутера и исходный статус сохраняют происхождение. Адаптер не записывает решений в исходную панель и не превращает старые материалы в подтверждение новой вакансии или встречи. По запросу владельца профили используются как вымышленные участники отдельного теста ДСА. При первом входе создаётся снимок шести профилей, готовые аккаунты и тестовые свободные слоты. Стартовый интерес к вакансии принят, но каждую встречу кандидат подтверждает вручную. Исходные «понравился / не подходит» остаются метаданными, а новые решения, встречи, чат и офферы сохраняются только в тесте HR Vision. «Сфера» остаётся отдельно.

`POST /api/hr/accounts` и `/session` принимают `scope: sfera | dsa` и требуют сохранённый доступ команды. Сессия привязана к подбору на сервере; подмена candidate/generation не даёт перейти в другой подбор. Старые сессии относятся к «Сфере». DSA-снимок и прогресс хранятся в `scenario_variants`, привязки сессий в `session_scopes`; таблица `scenario` и существующие данные не заменяются. Сброс обнуляет только текущий подбор и сохраняет его профили. Видео, запись, фидбек и офферы используют общий существующий процесс. Приёмник выкладки проверяет живые звонки во всех подборах.
