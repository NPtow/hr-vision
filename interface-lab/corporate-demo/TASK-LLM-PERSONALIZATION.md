# Задача: небольшая персонализация демо через LLM

Статус: сформулировано, подключение модели ещё не реализовано.

## Что согласовано

Модель докручивает текущую демонстрацию под задачу посетителя: несколько подписей в графе и нюансы существующих вымышленных профилей. Состав экранов, анимации, имена, аватары и порядок действий остаются заданными. Это не генератор интерфейса и не реальный поиск людей.

Если API недоступен, ответ задержался или не прошёл проверку, вся демонстрация использует готовый фиксированный сценарий: фиксированная задача, её требования, кандидаты и объяснения. Нельзя оставить произвольную задачу пользователя рядом с не относящимися к ней карточками.

## Проблема сейчас

`src/matching-demo.ts` распознаёт семь категорий регулярными выражениями. Запрос «Разобрать кучу лидов и уметь обзванивать 150 клиентов в день с хорошей конверсией» не превращается в подходящий сценарий: центр графа повторяет длинную исходную фразу, требования почти не меняются, профили остаются общими.

В `src/site.tsx` граф и поле задачи используют `need`, а отдельные сцены интереса, интервью и фидбэка содержат собственный сценарный текст. Подстановка должна иметь один источник данных, иначе разные экраны начинают рассказывать о разных задачах и людях.

## Минимальный результат модели

Вернуть один объект по строгой JSON-схеме, без Markdown, HTML, CSS и инструкций анимации:

```json
{
  "task_title": "Разобрать лиды и наладить обзвон",
  "criteria": [
    "Разбор входящих лидов",
    "150 звонков в день",
    "Конверсия звонков"
  ],
  "profiles": [
    {
      "id": "anna-mironova",
      "role": "Менеджер по работе с лидами",
      "strength": "Разбирает большой поток обращений",
      "reason": "Умеет выделять приоритетные обращения и доводить их до следующего шага.",
      "quote": "Сначала отделяю срочные обращения, затем собираю очередь звонков и фиксирую следующий шаг.",
      "gap": "Уточнить опыт темпа 150 звонков в день"
    },
    {
      "id": "mikhail-belov",
      "role": "Менеджер телефонных продаж",
      "strength": "Работает с интенсивным обзвоном",
      "reason": "Совмещает поток звонков с разбором причин отказа.",
      "quote": "Смотрю не только на количество звонков: отмечаю причины отказа и меняю следующий разговор.",
      "gap": "Согласовать целевой следующий шаг звонка"
    },
    {
      "id": "elena-orlova",
      "role": "Менеджер по развитию клиентов",
      "strength": "Повышает качество повторных контактов",
      "reason": "Использует историю обращений, чтобы каждый следующий контакт был предметным.",
      "quote": "Перед повторным звонком поднимаю прошлый разговор и готовлю конкретный повод связаться.",
      "gap": "Уточнить опыт массового обзвона"
    }
  ]
}
```

Это иллюстративные вымышленные детали, а не результат уже выполненного вызова модели. Идентификаторы фиксированы и связываются с существующими именами/аватарами. Конкретные числа из запроса сохраняются как требования: «150 в день» нельзя приписать кандидату как подтверждённый результат. «Хорошая конверсия» не превращается в выдуманный процент; нужно оставить уточнение о цели звонка.

Ограничения контракта: `task_title` — до 56 знаков; ровно 3 коротких критерия до 32 знаков; ровно 3 известных ID без повторов; `role` и `strength` — до 44 знаков; `reason` и `quote` — до 150; `gap` — до 80. `additionalProperties: false`; все поля обязательны. Ограничения проверяет сервер, а не только промпт. Набор полей можно сократить после первой проверки макета, расширение не требуется для v1.

## Куда подставляем

| Место | Данные |
| --- | --- |
| Центр графа | `task_title` вместо длинной сырой фразы |
| Узлы/подписи требований | `criteria` |
| Подсвеченные кандидаты графа | существующее имя + `strength` |
| Подборка и профиль | `role`, `strength`, `reason`, `gap` |
| Фрагмент демонстрационного интервью | `quote` того же профиля |
| Уточнение после просмотра | формулировка вопроса из `gap`; следующий кандидат берётся из того же сценария |

В сценах, где тот же кандидат появляется снова, нельзя показывать противоречащие заголовки, роли или факты из старого сценария. Фиксированные имена/аватары/сценические таймкоды остаются демо-атрибутами; реальные видео не генерируются. Существующая маркировка демо сохраняется. Мелкие пояснительные абзацы и служебные бейджи на лендинг не добавлять.

## Поведение

1. Посетитель редактирует задачу. Во время набора запросов к модели нет.
2. По кнопке «Показать кандидатов» или «Найти кандидата» запускается один запрос на готовый сценарий. Кнопка даёт короткую обратную связь; прокрутка и существующие сцены не ломаются.
3. После валидации единый `DemoScenario` атомарно передаётся в граф, карточки и связанные сцены. Компоненты не вызывают модель по отдельности.
4. Любая ошибка, отказ модели, невалидный JSON, несовпадение ID или превышение общего лимита ожидания переключают весь сценарий на `DEFAULT_SCENARIO`. Его задача — «Вернуть ушедших клиентов и навести порядок в B2B-продажах».
5. При fallback явно показывается «На примере» у задачи; исходный ввод сохраняется как черновик, но не выдаётся за персонализированный результат. Нет бесконечного спиннера и сообщений с технической ошибкой API.
6. Поздний ответ не подменяет уже показанный фиксированный сценарий. Новый ввод отменяет прежний запрос; устаревший ответ не может перезаписать новую задачу. Повторный проход одной и той же задачи использует тот же результат, чтобы история не менялась при прокрутке.

## Подключение

- Пользовательская ссылка ведёт в панель CLIProxyAPI, не задаёт конкретную модель.
- На облачном `/v1/models` проверено наличие `gpt-6-luna`. Предложение: проверить её первой. Доступность генерации, задержка и поддержка строгого `json_schema` пока не проверялись. Название модели хранить в серверной настройке, не в компонентах.
- Сайт сейчас статический. Понадобится узкий серверный endpoint, например `/demos/company-v1/api/personalize`, который обращается к `https://cliproxyapi.158-160-179-53.sslip.io/v1`.
- Ключ API хранится только на сервере. Management key, OAuth-файлы и URL административного интерфейса не нужны браузеру.
- В модель уходят только введённая задача и короткий шаблон вымышленного сценария. Контактные данные формы заявки не передаются.
- Ориентир для первого прототипа: до 3 секунд на ответ, общий предел ожидания 5 секунд; это цели проверки, не измеренные свойства модели. Нужны один запрос, ограниченный ответ, кэш по задаче/версии шаблона и лимит частоты обращений. Без инструментария агента и цепочек из нескольких LLM-вызовов.
- Сначала сделать маленькую проверку модели на нескольких задачах и недоступном API. Затем подключать UI. Не считать OpenAI-совместимый URL доказательством поддержки Structured Outputs.

## Приёмка

- На запросе про 150 звонков граф коротко передаёт смысл, сохраняет число и показывает отличающиеся по смыслу кандидатские нюансы.
- На задаче о CRM и на задаче о команде меняются не только заголовки, но и требования, сильные стороны и объяснения.
- Между графом, подборкой и открытым профилем совпадают кандидат, роль и обоснование.
- При выключенном API показывается полностью фиксированный сценарий; пользовательский текст не смешивается с ним.
- Невалидный/длинный/неполный JSON, неизвестные ID и поздние ответы дают предсказуемый fallback.
- Текст не ломает карточки на desktop, 390×844 и 320×568. Прокрутка, фидбэк и угловой таймер ведут себя по-прежнему.
- Ключей нет в JS-сборке; текущий публичный сайт не получает новое поведение до отдельной реализации и проверки.

## Очередность реализации

Проверка модели и JSON → контракт/`DEFAULT_SCENARIO` → серверный endpoint → единое состояние сценария → подстановка ограниченных полей → проверки fallback и интерфейса → локальный показ. В этом запросе сформулирована задача; LLM-интеграция не выполнена.
