# Готовый агент в HR Vision на YC

Решение: self-hosted Strands Harness, модель через существующий CLIProxyAPI,
Jev для поиска релевантных блоков интервью. Аккаунт AWS не требуется.
Strands выполняет агентный цикл, выбирает инструменты, управляет контекстом и
сохраняет состояние. Наш адаптер отвечает за права доступа, данные HR Vision,
ссылки на видео и связь с интерфейсом.

## Что остаётся в интерфейсе

Существующая вкладка «Помощник», её иконка и расположение остаются. Работодатель
пишет вопрос в то же поле. Ответ приходит постепенно; пока агент ищет данные,
показываем короткий статус: «Ищу в интервью» или «Сопоставляю с вакансией».
Ссылка на подтверждение открывает существующий видеоплеер в нужном месте.
После возвращения к кандидату восстанавливается его разговор. Доступны
«Остановить» для текущего ответа и «Новый разговор» для нового контекста.

## Точки подключения в коде

- `apps/web/src/scenes/interview-review/useInterviewAssistant.ts`:
  сейчас сообщения находятся только в React state. Добавить загрузку сохранённой
  беседы, поток ответа, восстановление выполняющегося запроса и остановку на сервере.
- `apps/web/src/scenes/interview-review/interview-assistant-api.ts`:
  запрос сейчас содержит источник, action, query и requestId. Для chat добавить
  conversationId и работу с runId. Режим search продолжает использовать Jev напрямую.
- `services/recruiting-api/employer_routes.py`:
  повторно использовать авторизацию и разрешение источника; сервер определяет
  вакансию, кандидата и запись. Идентификатор из браузера сам по себе не даёт доступа.
- `services/recruiting-api/interview_assistant.py`:
  заменить исполнителя chat через конфигурацию на клиент отдельного сервиса Strands.
  Существующий `evaluate_jev` сохранить инструментом поиска. Повторный requestId
  возвращает прежний run, а не оплачивает новый запрос к модели.
- `InterviewChatAnswer.tsx` и `interview-answer-model.ts`:
  использовать существующий вывод подтверждений. Сервер преобразует sourceId в
  разрешённую реплику и таймкод; модель не создаёт URL и координаты видео.

## Серверная схема

1. Отдельный сервис на YC, доступный только внутреннему API HR Vision.
   Не добавлять агентный цикл в обработчик веб-запроса или браузер.
2. Сессия принадлежит работодателю и связке «вакансия → кандидат → запись → версия
   расшифровки». Смена кандидата открывает другую сессию. Для сравнения кандидатов
   нужен отдельный разрешённый инструмент; смешивать их истории автоматически нельзя.
3. Инструменты: требования вакансии, профиль, действующая оценка с ограничениями,
   поиск Jev, соседние реплики. В боевом адаптере доступ проверяется при каждом чтении.
4. Сохранённые сообщения и состояние Strands лежат вне каталога релиза. Один активный
   запуск на сессию; повторные запросы, остановка и обрыв соединения имеют явные статусы.
   Смена версии расшифровки не оставляет старые ссылки активными без проверки.
5. Ключи модели и Jev остаются на сервере. Сервис имеет ограничение памяти, времени
   и числа вызовов инструментов. Браузер не получает административный API прокси.

## Порядок внедрения и проверки

1. **Пилот на YC:** синтетические данные, реальная модель CPA, реальный Jev,
   новый процесс на каждом сообщении. Проверяем инструменты, память разговора,
   ссылки, различие опыта и учебного кейса, разделение кандидатов.
2. **Подключение за флагом:** серверные инструменты получают реальные разрешённые
   данные. Внутренний тест в существующей вкладке без смены оформления.
3. **Сравнение:** старый помощник и Strands на одной модели, одинаковых вопросах и
   данных шести кандидатов. Оцениваем фактическую опору, полезность ответа, память,
   задержку и расход токенов. Тест пилота сам по себе не доказывает превосходство.
4. **Приёмка в браузере:** вопрос → уточнение → изменение приоритета → перезагрузка
   → другой кандидат → возврат. Отдельно: переход в видео, остановка, повтор запроса,
   отсутствие доказательств, отказ Jev, смена версии данных и отзыв доступа.
5. **Включение:** после этого направить chat на новый сервис. Флаг позволяет вернуть
   прежнего исполнителя без отката вёрстки. Перед постоянным запуском проверить
   запас памяти при ожидаемой одновременной нагрузке; пилот ограничен одним запросом.

## Граница текущего эксперимента

Синтетический пилот не читает рабочую базу и не подключён к браузеру. Восстановление
сессии после нового контейнера проверяет хранение разговора, но не заменяет проверку
перезагрузки UI, отмены запросов, длинного контекста и многопользовательской нагрузки.
Общая память между разными беседами пока выключена; её добавление требует отдельной
модели предпочтений работодателя и управления этой памятью.
