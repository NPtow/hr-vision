26 октября 2026. Исследован код ядра в `/Users/NIKITA/.codex/worktrees/assessment-services/HR Vision`, commit `c1e548d17d881097554df4c79d86d2388fab4974`. Это анализ локальной версии, не проверка текущего production. Вызовов JEV и записей в рабочие вакансии при исследовании не было.

## Что сейчас действительно работает

1. Авторизованный HR API создаёт обычную вакансию через `EmployerRoutes` → `employer_store.create_vacancy`. Владение — workspace работодателя; данные — `cp_vacancies.body`, версия/доступ — `em_vacancies`.
2. `vacancy_profile_bridge.snapshot` берёт **весь сохранённый body**, хеширует его и отправляет в отдельный `vacancy-profile`. Сам сервис не читает HR БД.
3. `vacancy_profile.engine.prepare` составляет один запрос JEV с **32 Choice-вопросами: 16 навыков × уровень и важность**. У всех один полный снимок вакансии. Уровни L1–L5 плюс «недостаточно данных»; важность I0–I3 плюс «недостаточно данных». Это два независимых вопроса, не 32 отдельных HTTP-запроса.
4. Сервис сохраняет исходный ответ и неизменяемый профиль. Есть ручные ревизии: `POST /v1/vacancy-profiles/{run_id}/revisions` с `expected_parent_id`, автором и изменениями `{parameter_id,required_level_id,importance}`. Старый ответ JEV сохраняется.
5. `recommendations_bridge` передаёт готовый профиль вакансии, профили кандидатов и **отдельные структурированные обязательные условия** в `recommendations`. Там уже нет модели: проверки условий, формула, сохранение результата. Текущая автоматическая политика в коде — `tanh-higher-v2`; уверенность модели не умножается на важность.
6. `recommendation_lifecycle` замечает изменения вакансии, профиля, фактов и пула. Открытые вакансии с отсутствующим/устаревшим профилем автоматически отправляет на JEV. Значит, при подключении нового входа требуется также изменить этот выбор пути; одного нового endpoint недостаточно.

## Где сегодняшний макет с этим расходится

| Макет | Код ядра | Что нужно соединить |
|---|---|---|
| Сессия чата с capability | Авторизованный workspace и vacancy_id | Серверная привязка к работодателю; capability локального макета не заменяет его авторизацию |
| `vacancy_context`: исходные факты с цитатами | Текстовые поля вакансии и отдельные `required_fields` | Сохранить контекст полностью, а обязательные условия нормализовать отдельно |
| Skill `parameter_id`, числовой `level`, `importance` | `parameter_id`, `required_level_id`, `importance` | Уровень брать по ID из закреплённого каталога, не парсить название карточки |
| Каталог JSON скопирован в макет | Каталог закреплён в релизах сервисов | Совпадают сейчас; нужен доступ через авторизованный API + версия и hash |
| Gemini предлагает навыки с качественной уверенностью | Профиль v1 обязательно содержит исходные Choice-ответы JEV | Нельзя притвориться JEV и создать фиктивные probabilities/usage |
| `confirmed=true` сохраняет локальный черновик | Нет входа готового подтверждённого профиля | Нужна команда передачи с квитанцией; сегодня подтверждение не публикует вакансию |
| Есть принятые, отклонённые и ещё не рассмотренные предложения | Recommender ждёт весь каталог; неизвестная важность блокирует сравнение | Нужны явные решения include/exclude/unresolved, а не автоматический ноль за отсутствие карточки |

Обычный employer create API **отклоняет** `requirements`/`required_fields`: они не входят в `VACANCY_FIELDS`. Manager-only маршруты `/api/hr/selection/.../profile/revisions` нельзя просто выдать работодателю: это другой доступ; сейчас автор ревизии там `manager`.

Ручная ревизия требует уже завершённый базовый JEV-run. Прямой профиль работодателя текущий recommender не примет: он проверяет модель `jev-*`, usage и оба raw Choice-ответа каждого параметра. Эти проверки полезны для модельного результата, но не описывают другой законный источник требований.

## Какой объект собираем в нашем сервисе

Три независимые части одного черновика:

- **`vacancy_context`** — должность, отрасль, город, формат работы, опыт, зарплата и прочие сведения. После извлечения сохраняются автоматически. У каждого значения источник/цитата; правка работодателя защищена. Это уже реализовано в макете как серверная проекция accepted-фактов, без второй изменяемой копии.
- **`skill_requirements`** — решение работодателя по каноническому навыку: включить/исключить/ещё не решил, требуемый level_id и importance. Навыки с Add по-прежнему требуют явного принятия. Уровень и важность — разные поля.
- **`mandatory_conditions`** — именно правила исключения, а не все упомянутые факты. Отдельное подтверждение делает их обязательными. Пример: «Москва» в описании ещё не означает «исключить всех вне Москвы».

Источники разговора/файлов/ссылок сохраняем отдельно, требования ссылаются на них. Исправленная пользователем формулировка хранится рядом с исходной, а не выдаётся за исходную цитату.

Действующее улучшение макета: новые автоматические факты имеют `automatic=true`, `hard_filter=false`, оригинальное предложение модели сохранено. Включить фильтр можно явно. Ранее принятые пользователем условия остаются без изменений. Ещё не принятые базовые сведения старых сессий переводятся в контекст один раз; принятые вручную и отклонённые записи защищены.

## Варианты подключения

**A. Минимальное изменение старого контракта.** Сохранить вакансию → дождаться JEV → наложить все подтверждённые решения через ручную ревизию → открыть сравнение. Raw JEV сохраняется; решение работодателя побеждает. Недостатки: даже полностью заполненный профиль зависит от доступности/времени JEV; нужно закрыть все 16 параметров и не пустить lifecycle считать промежуточный ответ модели. Больше стадий доставки, две версии данных до завершения.

**B. Готовый профиль — самостоятельный вход (предлагаю).** `vacancy-profile` принимает также подтверждённые требования с происхождением `employer_confirmed`. Общий результат для matching — канонические навыки/уровни/веса; raw JEV остаётся только там, где JEV реально вызывали. JEV может предлагать значения в ходе подготовки вакансии, но после подтверждения не становится обязательным пересказчиком решения работодателя.

Для B расширяем версионированный контракт и валидатор, не подсовываем fake JEV-run и не ослабляем валидацию v1. Модельные профили v1 продолжают работать; кандидатский assessment не меняется. Выбранные работодателем значения нельзя снова заменить выводом модели. Правка вакансии создаёт следующую ревизию и пересчитывает только подбор, без повторной оценки кандидатов.

## Предлагаемый путь передачи — ещё не реализован

1. Чат получает каталог навыков и допустимые обязательные поля через HR API. Черновик закрепляет `rubric_id`, `version`, `sha256`. Сейчас оба JSON действительно совпадают: 16 параметров, 80 описаний, версия `2026-10-26.behavioral-anchors.1`, hash `0a60df14697d677eaad8c90137cc4e5bfeb81462391f15d2b38983fe4d2e1e01`.
2. Подтверждение замораживает снимок: контекст, все решения по навыкам, обязательные условия, тексты/ссылки на сохранённые источники, цитаты, ручные изменения, версия каталога. Автор и workspace определяются сервером из авторизации, не из присланного JSON.
3. HR API принимает один `submission_id` + hash снимка. В одной своей транзакции сохраняет вакансию, факты, принятую ревизию и задание доставки. Незавершённая передача видна как `pending_profile`; в подбор её пока не пускаем. Повтор того же submission возвращает ту же квитанцию; другой payload под тем же ID даёт конфликт.
4. Durable worker через API передаёт снимок в `vacancy-profile`; сервис сохраняет неизменяемый подтверждённый профиль. Потеря HTTP-ответа восстанавливается повтором с тем же ключом. Для этого достаточно таблицы заданий/outbox; отдельный брокер здесь не обязателен.
5. HR адаптер закрепляет полученный `profile_id` только если ревизия ещё актуальна. При частичной ошибке хранит статус/повтор, а не сообщает «готово». После ACK профиль и связанные факты видны Верстаку одной согласованной версией.
6. Lifecycle использует подтверждённый профиль. Смена importance/level/facts делает старое сравнение устаревшим и запускает детерминированный пересчёт. Только HR команда запускает дальнейший рабочий подбор/доставку, если это требует отдельного действия; эта интеграция не отправляет приглашения.

Предлагаемые новые маршруты: employer `POST /api/hr/employer/vacancy-submissions` и GET квитанции; внутренний `POST /v2/vacancy-profiles/confirmed`. Названия — проект контракта, **таких маршрутов сейчас нет**. Не нужна отдельная публикация каждого плюса в production: до подтверждения это черновик своего сервиса.

## Что важно не потерять на твоём примере

- «SDR, Москва, удалённо, 3 года в edtech» — несколько разных сведений. Уточнение обязательности не должно мешать их автоматическому сохранению.
- В текущем справочнике обязательных отраслей есть logistics/it/finance/manufacturing/retail/professional-services, **нет edtech**. Нельзя молча превратить edtech в IT. Нужен канонический ID и такие же поля у кандидата; до этого — сохранённое исходное значение + требует уточнения.
- Локации и удалёнка сейчас лежат в одном массиве; matcher проверяет **любое пересечение**. `['ru:moscow','work-mode:remote']` означает «Москва ИЛИ удалёнка», не «удалёнка только из Москвы». Географию и формат работы нужно разнести в версии обязательных полей перед поддержкой такого ограничения.
- Общий опыт в продажах, отраслевой опыт, зарплата, разрешение на работу — разные условия. Текущий matcher реализует только географию, занятость и отраслевые месяцы. Нельзя показывать остальные как уже действующие жёсткие фильтры.
- Не добавленный навык не равен «явно не нужен». До полного подтверждения неизвестный остаётся unresolved. Если финальное действие означает «искать только по выбранным навыкам», это должно быть явно сказано; только тогда остальные можно оформить как employer-excluded с весом 0.
- Уверенность Gemini low/medium/high — основание уточнить предложение. Она не становится probability JEV и не участвует в формуле.

## Порядок реализации и проверка

Сначала каталог и контракт подтверждённых требований; затем employer submission/auth + доставка и адаптер; потом валидатор рекомендаций/lifecycle; последним подключаем кнопку передачи. Существующие raw/model профили и ручные ревизии сохраняем.

| Проверка до подключения | Ожидаемый результат |
|---|---|
| L4/importance3 выбраны работодателем | В сохранённом профиле и matching ровно L4/3, независимо от предложения модели |
| Повтор передачи / потерян ответ / рестарт | Один vacancy_id и одна ревизия; задача восстановилась, дубля нет |
| Другой workspace, устаревшая revision, несовместимый каталог | Отказ до изменения данных |
| Неизвестная важность или неоднозначный hard filter | Понятный incomplete/needs_review, не вес0 и не скрытый fail |
| Обновление после подтверждения | Старый score помечен устаревшим; новый использует новый profile_id; assessment кандидата не вызывается |
| JEV недоступен, профиль полностью подтверждён | В варианте B сохранение и дальнейший matching работают без нового вызова модели |
| Полный путь из сервиса работодателя до Верстака | Совпадают vacancy_id, каталог, уровень, важность, факты и source revision |
