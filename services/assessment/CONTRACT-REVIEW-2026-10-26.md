# Оценка интервью: разбор и контракт на согласование

Статус: **предложение, не новая реализация и не согласованная методика**.
Проверка production: 26 октября 2026, 02:18 МСК.
Владелец бизнес-решения: Никита. Сервис: `services/assessment`.

## Что произошло

Отдельный сервис уже существует: процесс `hr-vision-assessment`, приватный HTTP
`127.0.0.1:8096`, собственные очередь и SQLite, отдельные ключи и выпуск.
Он не читает HR-базу. Текущий выпуск:
`6c99b49e0514fe8658572047d88aa47a979602bb`, Jev `1.14.0`, пакет `2026-10-25.3`.
Нужно исправить его продуктовый контракт и расчёт, затем подключить потребителей
к одному результату. Создание ещё одного процесса само по себе дефект не устраняет.

Проверены две тестовые копии реальных интервью. Новых запросов к модели для
этого аудита не выполнялось; прочитаны сохранённые задания и ответы провайдера.

| Проверка | Кристина | Дина |
| --- | --- | --- |
| Фрагментов на входе | 185 | 178 |
| Критериев в выходе | 16 | 16 |
| Критериев, дошедших до числовой оценки | 5 | 8 |
| Последняя проверка `groundedness` | 0,12–0,59 | 0,22–0,56 |
| Порог публикации в коде | 0,75 | 0,75 |
| Опубликованных оценок / фрагментов | 0 / 0 | 0 / 0 |
| Состояние задания | completed | completed |

Механическая причина: `engine.assess()` при непрохождении последней проверки
одновременно обнуляет `level`, `modelEstimate`, `measurement` и `evidence`, затем
выдаёт всем одну фразу «недостаточно конкретных действий». Отсутствие материала
и несогласие проверяющей модели становятся неразличимыми.

Найден конкретный дефект контекста: для A03 Дины выбран `fragment-141`, а оценщику
переданы только `140..142`. Продолжение того же ответа — объёмы производства,
сроки решения и бюджет — находится в `143..145` и не участвует в оценке.
Это подтверждает обрезание эпизода. Причины каждого отказа `groundedness` ещё
требуют проверки на целых эпизодах; считать порог единственной причиной нельзя.

Ранее оригинальные карточки ДСА читали сохранённые проекции
`dsa-jev-preview-v1-380611` и `dsa-jev-preview-v1-378713`. Они содержат семь критериев,
шесть числовых `modelEstimate` у каждого из этих двух кандидатов и исходные цитаты.
Их `level` тоже был null: график показывал именно оценку модели. Новые регистрации
получили другой расчёт — 16 критериев, включая пять управленческих M01–M05.

В `OrbitGraph.tsx` количество >7 включает режим точек вместо подписей. Когда
нет ни одного `evidence`, график берёт все неизвестные критерии. Отсюда 16 пустых
точек. Это не случайная CSS-регрессия.

Дополнительно новый сервис не возвращает `feedbackQuestion`. Существующая панель
вопросов создаёт блоки только из фрагментов с этим полем; путь `screening` пока
допускает чтение оценки, но не сохранение ответа. Это надо включить в совместимость,
иначе замена оценки снова изменит уже согласованное поведение под видео.

## Граница сервиса и владельцы

Сервис отвечает за один результат: профессиональные действия в конкретной версии
интервью, оценённые по конкретной версии согласованной рубрики.

| Участник | Ответственность |
| --- | --- |
| HR API / адаптер | Права, tenant, выбор записи и основной расшифровки, проверка актуальности, постановка задания |
| Assessment | Разбор целых эпизодов, оценка по рубрике, проверка источников, результат и история вычисления |
| Сервис материалов / Core | Исходная запись, расшифровка и её версия |
| Сопоставление с вакансией | Отдельный результат поверх оценки навыков и явных требований; базовые баллы не меняет |
| HR-продукт | Ответы пользователя, заметки, решение по кандидату и показ результата |

Сервис не отправляет приглашения и не принимает решений о найме. Браузер не
передаёт ему ключи моделей и не задаёт произвольные промпты. Видеофайл для этой
версии не нужен: достаточно текста с привязкой к записи и времени.

## Предлагаемый вход

| Поле | Содержание и правило |
| --- | --- |
| `contractVersion` | Версия внешнего контракта, отдельно от версии методики |
| `tenantScope`, `subjectId` | Непубличные идентификаторы, назначенные авторизующим адаптером |
| `interviewId`, `recordingId` | Конкретное завершённое интервью и запись |
| `transcript.id`, `revision`, `sha256` | Точная версия выбранной расшифровки |
| `transcript.turns[]` | Полный текст: стабильный ID реплики, `speakerId`, `startMs`, `endMs`, `text` |
| `speakers[]` | Подтверждённая роль: candidate / interviewer / unknown. Не угадывать её по смыслу ответа |
| `chapters[]` | Существующие тематические блоки с ID, границами и названием, если они есть |
| `rubric.id`, `version`, `sha256` | Согласованные критерии и описания поведения для уровней 1–5 из реестра сервиса |
| `policyVersion` | Зафиксированные правила расчёта, агрегирования, проверки и используемые модели |
| `requestId` | Идентификатор запроса и трассировки |

Рубрика выбирается явно. Сервис не расширяет её сам до полного каталога и не
добавляет критерии руководителя к вакансии продавца. Название вакансии само по
себе не заменяет утверждённую рубрику. Неизвестная версия рубрики — ошибка входа.
Контакты, фотография и личные факторы не нужны для этого расчёта. Резюме сейчас
не смешиваем с доказательствами из интервью.

Первое предложение для сопоставимого пилота: прежние семь тем A01, A08, NEW-01,
A03, A11.1, A06.1, A07. Состав и поведенческие уровни нужно подтвердить отдельно;
наличие этих тем в старой витрине ещё не означает принятую методику. В старой
проекции у NEW-01 есть числовая оценка, хотя provenance говорит об отсутствии
якорей: этот разнобой также должен быть устранён до приёмки рубрики.

## Предлагаемый выход

| Поле | Что получает потребитель |
| --- | --- |
| `jobId`, `status` | queued / running / completed / failed / cancelled / expired |
| `assessmentId`, `revisionId` | Неизменяемый результат; пересчёт создаёт новую ревизию |
| `source`, `rubric`, `policyVersion` | Те же версии, на которых выполнен расчёт |
| `quality` | ready / partial / review_required: качество результата отдельно от завершения вычисления |
| `criteria[].id`, `label` | Только запрошенный состав критериев в стабильном порядке |
| `criteria[].state` | estimated / needs_review / not_observed / not_applicable |
| `criteria[].modelEstimate` | Число 1–5, метод и основание; именно оценка модели, не подтверждённая результативность человека |
| `criteria[].explanation` | Краткий вывод о конкретном действии кандидата, связанный с источниками |
| `criteria[].evidence[]` | Целые эпизоды: ID исходных реплик, точные цитаты, начало/конец, роль говорящего, тип основания |
| `criteria[].review` | passed / disputed / failed, конкретная причина и замечания к оценке |
| `criteria[].missingReason` | Например no_relevant_episode / speaker_unknown / incomplete_source; не общий текст на все случаи |
| `criteria[].feedbackQuestions[]` | Вопрос по конкретному эпизоду, его ID и временные границы для уже существующей панели под видео |
| `provenance` | Запрошенная/фактическая модель, промпт и его хеш, время, стоимость/usage, покрытие, стадии |
| `error` | Машинный код, стадия, возможность безопасного повтора; не подмена результатом «нет навыка» |

Смысл состояний:

- `estimated`: есть относящиеся к критерию действия и воспроизводимая оценка модели.
- `needs_review`: источник найден, но есть конфликт или сомнение в интерпретации.
  Источник сохраняется; предварительная оценка и замечание проверки хранятся раздельно.
  Предложение для UI: показывать число как оценку модели с обозначением спорности.
- `not_observed`: в данном интервью не найден подходящий материал; число null.
- `not_applicable`: критерий явно исключён областью рубрики; число null.

Неверная цитата, чужая реплика, другой transcript hash или выдуманный таймкод
блокируют публикацию соответствующей оценки. Простое несогласие второй модели
с баллом не стирает настоящую цитату. Неопределённость не становится нулём.
Вероятность проверяющей модели не является вероятностью успеха человека на работе.

Шкала остаётся 1–5; распределение вероятностей сохраняем, только если модель
действительно его возвращает. Формулу свёртки нескольких эпизодов фиксируем в
версии методики после разбора примеров: без скрытых ограничений и усреднения
противоречащих эпизодов. Эта формула пока **не согласована**.

## Обработка и протокол

1. HR сохраняет намерение обработки в своей транзакции и передаёт снимок источника.
2. Сервис валидирует вход и получает эпизоды из полного интервью: вопрос, полный
   ответ, релевантные уточнения. Соседние строки не считаются автоматически целым эпизодом.
3. Оценщик рассматривает все относящиеся к навыку эпизоды по одной рубрике.
4. Проверка отделяет валидность источников от несогласия с оценкой.
5. Сервис сохраняет результат и диагностические стадии; адаптер проверяет версии
   источника и прав перед публикацией в HR.

Предлагаемые версионированные операции: `POST /v2/assessments` → job,
`GET /v2/jobs/{id}` → состояние и результат, `DELETE /v2/jobs/{id}` → отмена/удаление
в рамках политики хранения. Это предложение, endpoints ещё не реализованы.
Существующие v1 работают до проверенного переключения адаптера.

Ключ вычисления: tenant + стабильная идентичность источника + transcript hash +
rubric hash + policy/model versions. Открытие страницы, изменение контакта и
повтор доставки не запускают новый платный расчёт. При неизвестном исходе POST
ищем существующее задание; не запускаем автоматически другую модель.

Остаются текущие отдельный runtime, БД, Bearer между сервисами и долговечная очередь.
Без новой инфраструктуры сохраняем действующие ограничения: 600 фрагментов,
220 КБ входа, 100 активных заданий, 5 новых заданий субъекта в сутки, 55 секунд
на вызов и 600 секунд до старта последней стадии. Полные реплики могут потребовать
пересмотра лимита длины одного фрагмента; это проверяется на шести интервью до
фиксации JSON Schema. Текущее хранение входа 7 дней, результата 90 дней.
Не заявляем эти лимиты подтверждённым SLA.

## Потребители и переход

Нужно проверить зарегистрированного кандидата (`screening`), импорт ДСА (`intake`),
публичный профиль и сопоставление с вакансией. Встречи после первого интервью
пока возвращают пустую оценку: поддержка дополнительных интервью требует
отдельно согласованного расширения, не включается незаметно.

Адаптер преобразует один контракт в существующие `AssessmentPresentation` и
вопросы под видео. Вёрстку сохраняем. Состав Орбиты определяется согласованной
рубрикой и явным состоянием оценки; полный каталог не подставляется при пустом результате.
Для `screening` нужно обеспечить сохранение ответов так же, как для `intake`.

Новая версия сначала работает на шести реальных интервью в отдельной ревизии,
не перезаписывая опубликованные оценки. Переключение через штатный адаптер после
сравнения результатов; откат возвращает прежнюю ревизию только для той же версии
источника. Несовместимый или устаревший результат не используется как fallback.

## Что нужно согласовать перед реализацией

1. Состав рубрики пилота: прежние семь тем или другой явно заданный набор.
2. Показ предварительной оценки модели вместе с найденным эпизодом и статусом
   проверки; null только при отсутствии допустимого основания. Спорные оценки
   видны как спорные, а не как «нет данных».
3. Вход и выход выше; правила уровней/агрегирования проверяем на конкретных
   эпизодах и утверждаем до переключения production. Модель выбираем по результатам
   сопоставимого пилота (Jev и доступная CPA), без автоматической подмены провайдера.
