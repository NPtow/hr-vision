# Новое ядро оценки: первый самостоятельный контур

Решение 26 октября 2026: **весь корпус кандидата → отдельный вопрос JEV на каждый
параметр → распределение по собственным уровням параметра + «недостаточно данных»**.
Несколько независимых вопросов отправляются одним запросом с общим полным `state`.

Это отдельный Python-пакет без зависимостей от старого Go-ядра и `interface-lab`.
Реализованы корпус, формат шкал, построитель запроса, проверка ответа, журнал запусков,
CLI и приватный HTTP-процесс с очередью. Существующий сборщик подключён через
HR-адаптер; чтение CV и основных расшифровок проверено на YC без вызовов модели.
Верстак подключается через `assessment_core_bridge.py` и флаг `HR_ASSESSMENT_CORE_ENABLED`.
Поставка и отдельный процесс описаны в [deploy/README.md](deploy/README.md).
Точки запуска/чтения и контракт интеграции: [API.md](API.md).
Состав источников, проверки и фактический срез: [COLLECTION.md](COLLECTION.md).

## Запуск

Python 3.9+, установка пакетов не нужна. Из корня HR Vision:

```bash
export PYTHONPATH=services/assessment-core
python3 -m assessment_core plan \
  --corpus services/assessment-core/examples/corpus.synthetic.json \
  --rubric services/assessment-core/examples/rubric.synthetic.json \
  --request-only --output /tmp/assessment-request.json

# Единственный новый платный запрос. Пример полностью синтетический.
python3 -m assessment_core run \
  --corpus services/assessment-core/examples/corpus.synthetic.json \
  --rubric services/assessment-core/examples/rubric.synthetic.json

# Воспроизведение из сохранённого ответа: сеть и ключ не требуются.
python3 -m assessment_core replay RUN_ID

python3 -m unittest discover -s services/assessment-core/tests -v
```

Ключ читается внутри клиента: `ASSESSMENT_CORE_JEV_API_KEY`, затем существующий
`ASSESSMENT_JEV_KEY`, `JEV_API_KEY`, `TYPESAFE_API_KEY`, `HR_JEV_API_KEY`, затем
`JEV_API_KEY_FILE` или `~/.config/jev/api-key`. Значения не печатаются.
Модель задаётся явно (`--model`, default `jev-1.14.0`), алиасы запрещены оценщиком.

По умолчанию журнал: `~/.local/share/hr-vision-assessment-core/runs.sqlite3`.
Можно передать `--db`. В нём сохраняются полный вход, точный запрос, полный
проверенный JSON-ответ провайдера, результат, модель и usage. Это приватные данные;
каталог создаётся с 0700, база с 0600. Текущий журнал автоматически ничего не стирает. Политика срока хранения и удаления
вместе с кандидатом остаётся отдельной задачей; публичного доступа к журналу нет.

## Контракт входа и результата

`examples/corpus.synthetic.json` показывает нормализованные источники. Одна
переданная единица источника = один чанк. Сохраняются даже пустые единицы, точный
текст, порядок, роли и таймкоды. Нет обрезки, удаления строк или догадок об авторе.
Fingerprint охватывает нормализованные единицы, не исходный бинарный PDF/видео.
Принадлежность источников кандидату и полноту выгрузки должен проверять серверный
адаптер HR; одно поле `candidate_id` само по себе этого не доказывает.

`examples/rubric.synthetic.json` — учебная шкала для технического теста.
Каждый параметр имеет `parameter_id`, название, определение и **собственные**
2–10 уровней с ID, названием и самостоятельным описанием. Никакие наши рабочие
уровни по умолчанию в код не зашиты. Версия и полный hash шкалы входят в ID запуска.

Для каждого параметра выход содержит:

- `selected_level_id` — выбранный ID уровня или null;
- `status` — `assessed` / `insufficient_data`;
- `levels[].probability` — исходные вероятности всех уровней;
- `insufficient_data_probability` — вероятность отдельного варианта;
- `model_confidence` — исходная уверенность JEV в распределении.

Используется `Choice`, потому что «недостаточно данных» не является ступенью
числовой шкалы. Вероятности не перенормируются после удаления этого варианта,
не умножаются на confidence и не превращаются в итоговый балл вакансии.
Confidence — характеристика ответа модели, не измеренная точность на наших интервью.
Ошибки API сохраняются как ошибки запуска, не как `insufficient_data`.

### Вопросы «да/нет» и будущий анализ вакансии

В `providers/jev.py` также перенесён Noul-контракт существующего аналитического
сервиса (`services/assessment/engine.py`, `validate_response` в checkout
`candidate-public-profile`). Один запрос может содержать Noul, Choice и Score;
все вопросы получают тот же полный `state`. Noul сохраняет только исходную
вероятность ответа «да» (`noul` от 0 до 1), без придуманного confidence и без
автоматического превращения в решение по кандидату. Проверены отсутствие и
наличие описаний true/false, смешанный пакет, точный состав ответов и отклонение
некорректных значений до/после transport. Сеть в этих тестах подменена.

Это готовность клиента к первой версии по образцу JEV-анализатора, а не подключённый
расчёт важности вакансии. HTTP `/v1/assessments` по-прежнему оценивает только
кандидата через Choice. Веса, требуемые уровни, вопросы обязательности и политика
сопоставления не зашиты в этот endpoint. Поддержка Score клиентом также не меняет
выбранный формат кандидатской оценки.

Независимые вопросы можно объединять. Если ответ «выполняет ли кандидат условие»
должен использовать требуемый уровень, который ещё вычисляется другим вопросом,
его надо передать следующим запросом либо использовать заранее сохранённый
профиль вакансии: вопросы одного пакета не получают ответы друг друга.
Основание: [System One](https://docs.typesafe.ai/api/system-one),
[Noul](https://docs.typesafe.ai/primitives/noul). Важность, необходимый уровень
и обязательность остаются разными величинами; числовая формула ещё обсуждается.

## Повторные запуски и ограничения

Идентичный завершённый запуск читается из журнала без вызова JEV. После таймаута
или прерванного вызова автоматической повторной отправки нет. Сохранённый ответ
можно снова интерпретировать без сети. Проверяются hashes, соответствие запроса
корпусу/шкале и версия контракта; повторное чтение не переписывает результат
другой методикой. Ручной повтор после неизвестного исхода требует отдельного
явного механизма; он пока не реализован.
HTTP-сервис и CLI используют исключительное владение базой. В очередь помещаются
до 100 ожидающих/активных запусков; у процесса один потребитель. При перезапуске
сохранённый ответ восстанавливается без сети, неподтверждённый вызов не повторяется.

Клиент ограничивает HTTP-тело 4 MiB (это байты, не токены), блокирует redirects и
не подхватывает ambient proxy. Старый analytics runtime умеет явный loopback SOCKS;
эта конфигурация ещё не перенесена, deployment через такой egress пока не проверен.
Полный корпус никогда не сокращается ради лимита. Контекстные ограничения JEV —
отдельная граница: 32k tokens для state + одного вопроса, 64k для всего запроса по
документации на дату проверки. Нет silent fallback на retrieval или экспериментальный
long context. До подключения больших интервью нужен проверенный расчёт размера
контекста и явная политика обработки отказа провайдера.

## Проверено

Локальные тесты покрывают полный корпус, собственные шкалы, сохранение отсутствия
данных, строгий typed ответ, конкурирующие запуски, неоднозначный исход запроса и
replay без сети. HTTP-механика нового клиента проверяется подменённым transport.

Один живой запрос 26 октября 2026 выполнен штатным `jev/scripts/jev.py` с payload,
созданным новым `prepare`: 2 параметра, один синтетический CV и интервью. Получен
`jev-1.14.0`, 3462 input tokens / 112 output tokens. По возражению выбран L3, по
развитию сотрудников — `insufficient_data`. Ответ проверен новым валидатором,
сохранён новым RunStore и успешно воспроизведён без API. Артефакты лежат в
`output/research/core-redesign-20261026/jev/contract-smoke/`.
Это проверка контракта, не качества рабочих шкал и не тест реальных кандидатов.
