# Автоматическая обработка кандидатов

HR API владеет авторизацией, анкетой, связью кандидата с материалами и журналом
команд. Core хранит записи и выбранные расшифровки. `assessment-core` отдельно
выполняет оценку полного корпуса через JEV; `vacancy-profile` отдельно оценивает
требования вакансии; `recommendations` вычисляет соответствие без модели.
У этих трёх сервисов собственные процессы, API, базы результатов и выпуск.
Ни один из них не подключается к HR SQLite напрямую.

## Независимая готовность материалов

`selection_materials_lifecycle` — наблюдатель внутри HR API, а не ещё один сервис
оценки. Он читает Core, обходит кандидатов с интервью и сохраняет только метаданные
в `sl_evidence`, `sl_materials_cursor`, `sl_materials_checks`.
Для него не нужны настройки JEV, CV или запущенная оценка.

Готовность требует завершённого HR-интервью, готовой видеозаписи и выбранной
готовой расшифровки каждой части записи. Новая часть, отзыв доступа, неготовый
канал или ошибка чтения снимают готовность. Закрытая комната сама по себе не
подтверждает интервью. Неизвестные количества остаются `null`.

Сверка по умолчанию идёт каждые 30 секунд пакетами по 10 кандидатов. Курсор
сохраняется после каждого кандидата; следующие пакеты обрабатываются до конца
обхода. Ошибки получают сохраняемую задержку 5–120 секунд. Метаданные готовности
старше 120 секунд считаются непроверенными. Это срок свежести, а не обещание
пропускной способности при произвольном размере каталога. Карточка также сверяет
материалы через GET; её открытие не запускает модель или ASR.

## Долговечная очередь оценки

`assessment_core_lifecycle` хранит команды и подтверждения в HR DB.
Сборщик передаёт CV и все интервью/встречи из канонического досье; частичный
корпус не отправляется. Каждый параметр получает один и тот же полный корпус.
Ключ работы включает кандидата, версию корпуса, шкал, модель и формат запроса.

- Повторный обход или рестарт не создаёт повторную оценку того же входа.
- После подтверждённого запуска временная ошибка GET вызывает задержку
  5–300 секунд, затем повторное чтение. Через 600 секунд показывается задержка,
  но уже принятый расчёт не теряется.
- Успешное чтение обнуляет счётчик последовательных ошибок.
- При неизвестном исходе POST или провайдера работа требует проверки; слепого
  повторного запуска нет.
- При смене исходников старый результат остаётся историей. Возврат к прежнему
  корпусу повторно использует его результат. Текущая привязка хранится отдельно
  от времени создания и обновления исторических расчётов.

## Анкетные факты

Подтверждённое сохранение анкеты оставляет происхождение каждого поля.
Непроверенные старые значения, вывод модели и город проживания не превращаются
в подтверждённые условия работы. Для вакансии известные город и занятость
показываются отдельно от ещё неизвестной обязательности.
Ручная правка меняет отдельные поля. Если затем изменился их источник, возникает
явный конфликт; остальные поля продолжают обновляться из анкеты.

## Конфигурация и диагностика

- `HR_CORE_CATALOG_ENABLED=1` включает наблюдатель материалов по умолчанию.
  `HR_SELECTION_MATERIALS_ENABLED=0` позволяет отдельно остановить его.
- `HR_SELECTION_MATERIALS_BATCH_SIZE` / `HR_SELECTION_MATERIALS_INTERVAL_SECONDS`
  задают размер пакета и период. Используются существующие Core URL/key.
- `HR_ASSESSMENT_CORE_AUTO_ENABLED=1` и
  `HR_ASSESSMENT_CORE_AUTO_ALL_COMPLETED_HR=1` включают общий обход завершённых
  интервью без списка из трёх профилей. Без второго флага сохраняется прежняя
  явно заданная область по ID/дате. Флаг не обходит проверки полного корпуса.
- `GET /api/hr/selection/status` доступен только менеджеру: состояние обоих
  наблюдателей, очередь, курсоры и ошибки. Успех HTTP `/health` сам по себе
  не доказывает работоспособность конвейера.
- Список и карточка возвращают `automation` отдельно от готовности материалов
  и сохранённой оценки. В ответах нет токенов и текста интервью.

Перед выпуском нужен обновлённый root-owned `receiver.py`: архив теперь включает
`selection_materials_lifecycle.py`. Старый полный набор сохранён как допустимый
формат отката. Публикация остаётся через штатный CI с проверкой активных звонков,
резервной копией и восстановлением предыдущего релиза при ошибке.

Независимые алгоритмические проверки используют временные базы, HTTP-источники
и синтетический ответ провайдера. Они проверяют передачу и обработку, не качество
оценок JEV. Разработка в этом изменении выполнялась с согласованным исключением
из защищённого developer runner; полный строгий isolated-testing PASS не заявлен.
