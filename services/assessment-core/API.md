# Контракт нового оценщика — full-corpus-level-choice-v1

26 октября 2026. Приватный процесс и интеграция с существующим Верстаком. Один кандидат и одна версия корпуса на запуск. Все параметры видят
весь переданный корпус. Рабочие шкалы передаёт серверный вызывающий компонент.

## Запуск и чтение

Из корня проекта: `PYTHONPATH=services/assessment-core python3 -m assessment_core.api`.
Процесс слушает только `127.0.0.1:8097`; порт меняет `ASSESSMENT_CORE_PORT`.
`ASSESSMENT_CORE_SERVICE_TOKEN` — 64 шестнадцатеричных символа, выдаётся серверному
адаптеру, не браузеру. `ASSESSMENT_CORE_MODEL` — фиксированная версия модели;
`ASSESSMENT_CORE_DB` — отдельный SQLite файл. Конфигурация JEV описана в README.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/healthz` | Проверка HTTP-процесса; не проверка доступности JEV |
| POST | `/v1/assessments` | `{corpus, rubric}` → записать снимок и поставить в очередь |
| GET | `/v1/assessments/{run_id}` | Статус и сохранённая оценка |

POST/GET требуют `Authorization: Bearer <service-token>`. POST принимает
`application/json` и известный Content-Length, не более 4 MiB. Секрет нельзя
передавать в URL. Источник входной структуры — примеры `examples/*.synthetic.json`.

Ответ POST — HTTP 202; повтор идентичного тела возвращает тот же `run_id`, в том
числе уже завершённый. GET — HTTP 200. Общая оболочка:

```json
{
  "run_id": "<sha256>",
  "status": "queued",
  "assessment": null,
  "error": null,
  "corpus_revision": "<sha256 normalized corpus>",
  "rubric_version": "<supplied rubric version>",
  "model": "jev-1.14.0"
}
```

Статусы: `queued`, `sent`, `response_saved`, `completed`, `failed`,
`outcome_unknown`. `sent` означает сохранённое намерение внешнего вызова;
`response_saved` — ответ получен, результат ещё не собран. После аварийного
завершения `sent` становится `outcome_unknown`, автоматически не отправляется
повторно. `response_saved` восстанавливается из сохранённого ответа без сети.
`insufficient_data` — **исход отдельного параметра**, не статус фоновой задачи.

Коды HTTP: 401 авторизация, 404 неизвестный маршрут/запуск, 408 время чтения
запроса, 413 размер, 422 формат/валидация, 503 локальная недоступность/полная очередь.
Ошибка JEV возникает после постановки и видна в `status/error` через GET.
Отказ JEV никогда не подменяется оценкой человека. Исходные тексты и ответ провайдера
не выдаются этим HTTP API; полный снимок хранится в приватном журнале.
Полученные, но отклонённые клиентом ответы сохраняются отдельно в приватной таблице
`provider_rejections`, включая некорректный JSON. HTTP-ответ клиенту содержит только
безопасный код ошибки. Повторный платный запрос автоматически не запускается.

`context_limit` с HTTP 400 сохраняет точную машинную причину JEV
`max_tokens_exceeded`. Текст не обрезается, experimental long context не включается.
В формате запроса `compact-provenance-v1` общие `state.sources` и `state.chunks`
используют короткие ссылки s1/c1 по порядку полного корпуса. Тексты, роли, имена
говорящих и таймкоды копируются без изменений; исходные ID, версии и хеши сохраняются
в `plan.corpus` и однозначно восстанавливаются по порядку. Это сокращает служебную
метаинформацию, а не материал для оценки. Формат входит в идентичность запуска.

## Завершённая оценка

`assessment` содержит `run_id`, `candidate_id`, `contract_version`,
`corpus_sha256`, `sources`, `chunk_count`, `rubric_id`, `rubric_version`,
`rubric_sha256`, `model`, `usage` и `parameters`.

Каждый элемент `parameters`:

```json
{
  "parameter_id": "<stable parameter ID>",
  "title": "<parameter title>",
  "status": "assessed",
  "selected_level_id": "L3",
  "levels": [
    {"level_id":"L1", "label":"...", "description":"...", "probability":0.10},
    {"level_id":"L2", "label":"...", "description":"...", "probability":0.20},
    {"level_id":"L3", "label":"...", "description":"...", "probability":0.60}
  ],
  "insufficient_data_probability": 0.10,
  "model_confidence": 0.4666667
}
```

Числа выше иллюстративные. Все вероятности, включая insufficient_data, сохраняются
без перенормировки. Если выбран insufficient_data, `selected_level_id=null`,
`status=insufficient_data`. Не превращать это в 0 баллов. Никакой скрытой числовой
оценки или vacancy score в ответе нет. Результат Choice не содержит объясняющих
цитат: `sources` — перечень всего переданного материала, а не доказательства,
выбранные моделью для конкретного параметра.

## Существующий сборщик: реализованный серверный адаптер

`services/recruiting-api/assessment_corpus.py` и операторская команда `collect_hr.py`
переиспользуют эти чтения. Подключение проверено на живых данных YC; модель не
вызывалась. Полный контракт, ограничения и пример: [COLLECTION.md](COLLECTION.md).

Проверено по checkout `speechkit-pipeline` 26 октября; там продолжается работа
над первичной расшифровкой, эти файлы здесь не менялись:

- `services/data-core/src/hr_materials_core/app.py`:
  `GET /v1/candidates/{candidate_id}/dossier` уже собирает интервью и встречи.
- В `repository.py` dossier раскрывает все варианты текстов и сведения о выборе.
  Использовать `primary-transcripts`, его выбранные ID/hash и поколения.
- `cp_resumes.text_content` уже содержит извлечённый CV. Dossier отдаёт только
  метаданные CV, поэтому текст должен добавить авторизованный адаптер владельца
  этой таблицы. Новый PDF/ASR парсер внутри оценщика не нужен.

Отображение в наш DTO:

| Поле | Как получает серверный адаптер |
|---|---|
| candidate_id | Авторизованный ID кандидата |
| source_id | Устойчивый ID владельца + записи / CV |
| version | Выбранный transcript ID, content hash, поколение выбора; для CV hash текущего текста и revision |
| kind | `cv` или `interview` |
| unit_id | Устойчивый номер сегмента внутри неизменяемого текста; у Core сейчас нет ID сегмента |
| text/speaker/start_ms/end_ms | Копия выбранных сегментов без выкидывания строк |
| role | Из достоверной связи участника; иначе unknown/null |

Core `content_sha256` и новый normalized-source hash — разные хеши разных
структур. Хранить оба в интеграционном манифесте, не подменять один другим.
Внутренние чанк-ID разрешать только в контексте candidate/corpus revision.

Перед отправкой адаптер сверяет ожидаемый состав интервью и частей записей с
выбранными готовыми текстами. Один `primary.status=ready` недостаточен: он может
относиться только к ранее включённым записям. Нельзя молча исключить вторую часть
интервью или незавершённую расшифровку. Корпус включает CV, все `interviews[]` и
`meetings[]`, привязанные Core к кандидату: интервью работодателя также не должно
потеряться. Ещё не состоявшиеся записи без материалов отражаются как `not_conducted`.
Подтверждённое отсутствие записи — `not_recorded`; неизвестность и ошибки блокируют
сборку. Эти состояния остаются в отдельном манифесте, не превращаются в текст.

Перед публикацией адаптер повторно проверяет право доступа и актуальность
источников. Изменение CV/primary transcript даёт новую ревизию; старую оценку нельзя
показывать как актуальную. Старый `assessment_jobs.Bridge.snapshot` с одной записью,
одним текстом и без CV не соответствует этому контракту.

Фронт и HR-проекции подключаются владельцем «Верстака». Публичный экран уже
существует; этот сервис возвращает новую оценку, не старый
`engine-v1/candidate_profile/1` и не изменяет стадии подбора/приглашения.
