# Расчёт соответствия в рабочей системе

Сервис recommendations 1.2.0, политика `tanh-higher-zero-v3` (`AUTO_POLICY`). Расчёт алгоритмический; JEV отдельно оценивает кандидата и требования вакансии. Открытие Верстака не запускает модель и не пересчитывает числа в браузере.

Для навыка, где выбран числовой уровень, нормируем сохранённые вероятности пяти уровней: `q_l = p_l / sum(p_1..p_5)`. Исходные вероятности, неизвестность и confidence сохраняются. Confidence не является множителем. При выбранном «недостаточно данных» навык исключаем из числителя и знаменателя; это не нулевой уровень.

Если требуемый уровень `r` известен, полезность уровня `l` равна `u_l = tanh(l-r)` при k=1. Если требование отсутствует, используем `u_l = 2*(l-1)/(N-1)-1`: для пяти уровней −1, −0.5, 0, 0.5, 1. Отсутствующее требование остаётся null. Линейное расстояние между уровнями — правило выбранной политики, а не результат статистической калибровки.

```
m_i = sum(q_il * u_il)
W = sum(w_i)                    # учтённые навыки, важность 0..3
score = sum(w_i * m_i) / W
score_points = 50 * (score + 1)
weight_share_i = w_i / W
score_points_contribution_i = weight_share_i * 50 * (m_i + 1)
```

Вклады в баллах суммируются в итог. При известном требовании 50 означает баланс относительно требуемого уровня; без требования 50 соответствует середине шкалы. Это не вероятность успешного найма. Важность меняет долю навыка в итоговом результате, а не оценку навыка кандидата.

Пример: кандидат имеет уровни 4 и 2 с вероятностью 100%, требования 3 и 3, важности 3 и 1. Получаются `m = +0.761594` и `−0.761594`; доли 0.75 и 0.25. Вклады — 66.059781 и 2.980073 балла, итог **69.039854 из 100**. При равных важностях результат был бы 50. Исходный `score=+0.380797` также сохранён.

Важность 0 исключает навык с причиной `zero_importance`. По согласованному правилу v3 неизвестная важность также исключает навык, с эффективным `weight=0` и отдельной причиной `unknown_importance`. Поле `source_importance` сохраняет исходное значение — `insufficient_data` либо число. Снимок вакансии, её статус `needs_review` и сырые ответы модели не изменяются. Coverage считает эффективные веса и число исключённых навыков. При отсутствии всех пригодных навыков результат `null/unscored`, не 0 и не 50. Обязательные условия проверяются отдельно и не меняют формулу; автоматическая оценка не отправляет приглашения и не принимает решение о найме.

При неизвестном требовании прямые баллы уровня кандидата равны `100*(l-1)/(N-1)` — для пяти уровней 0, 25, 50, 75, 100. Усредняем их по `q`, умножаем на известную важность и делим на сумму учтённых весов; это та же записанная выше формула с signed utility и финальным `50*(score+1)`. Фиктивного требования нет, tanh относительно неизвестного уровня не применяется. Старые `tanh-v1` и `tanh-higher-v2` продолжают отклонять неизвестную важность, а сохранённые результаты остаются неизменными.

HR API по умолчанию ведёт фоновый обход всех активных вакансий. Для каждой берётся весь пул кандидатов с готовыми записью и текстом HR-интервью. Если оценки кандидата ещё нет, показывается ожидание; отдельный lifecycle оценки кандидата готовит её по полному корпусу. После появления результата сравнение выполняется автоматически. Пул больше 1000 явно отклоняется, а не обрезается.

Новый кандидат, изменение вакансии, материалов, профиля, фактов или политики делают прежнее сравнение устаревшим. Worker сохраняет очередь обхода, состояния и интервалы повторов в БД, восстанавливается после перезапуска и не повторяет оценку JEV для неизменных входов. Цикл по умолчанию — 30 секунд между обходами; время внешних сервисов добавляется отдельно. Верстак читает серверные результаты и обновляет видимую вкладку автоматически.

Ручной production-прогон в этом выпуске не выполняется: после выкладки работу инициирует сам код. Проверки — синтетические алгоритмические и компонентные сценарии, независимый runtime sandbox и штатные проверки выпуска; это не подтверждение точности модели на реальных интервью.
