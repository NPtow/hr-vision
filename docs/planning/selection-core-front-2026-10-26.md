# Подготовка фронта к новому ядру

26 октября 2026. Реализовано локально в `codex/selection-core-readiness`, основа
`9f587423` из `origin/main`. Это подготовка интерфейса и чтения статусов, не
переключение production на новый оценщик. Дополняет, а не заменяет исторический
план [таблицы подбора](candidate-selection-workbench-2026-10-25.md).

## Разделение работы, принятое пользователем

- **«Ядро»**: новый оценщик, методика и рабочие шкалы; ревью состояния БД и
  существующей сборки источников. Отчёт БД от 25 октября передан вместе с точными
  файлами dossier, primary-transcripts и публичной проекции.
- **«Верстак»**: фронт, выбор серверных API, адаптеры проекций, точные статусы;
  приёмка и внедрение готового ядра.
- **«МикроТрансрибация»**: импорт и выбранные основные расшифровки. Её работу
  со связями файлов и кандидатами здесь не дублируем.
- Завершение регистрации и согласование кандидатом остаются в существующем
  потоке «Работодатель/Подборка».

## Что уже изменено

Операторский вход остаётся `hr-vision-product--manager&workspace=selection`.
«Кандидаты» и «Подборка» показывают одни и те же ID людей, с разными столбцами.
Это две проекции списка, не две базы и не копии кандидатов. Вакансия выбирается
из существующего `GET /api/hr/selection/vacancies`.

В подборке отдельно видны материалы, оценка навыков, сравнение с вакансией и
согласование. Есть фильтр состояния расчёта; старые фильтры почты/Telegram
сохранены. Карточка открывается в существующей боковой панели.

- `cp_interviews.status=completed` называется **«Встреча закрыта»**. Этот флаг
  не доказывает разговор, присутствие двух участников или наличие видео.
- Сохранённый расчёт в списке называется **«Расчёт сохранён»**. При открытии
  карточки проверяется его актуальность; ошибка источника не подменяется старым
  результатом. Чтение таблицы не делает сетевой запрос на каждого кандидата.
- Отсутствие сопоставления называется **«Не сравнивали»**, а не отрицательной
  рекомендацией. Смена вакансии может сделать сравнение устаревшим, не изменяя
  оценку навыков человека.
- `unknown`/`insufficient_data` не становятся нулевым баллом. Старый engine-v1
  находится в свёрнутом блоке «Архивная оценка».
- Новый расчёт в `as_bindings` имеет приоритет над старым `sl_core_results`.
  Pending/failed нового расчёта не возвращает старую рекомендацию для отправки.
- Просмотр карточки, обновление и проверка актуальности не вызывают модель,
  не создают подборку и не отправляют приглашения.

## Выбранные backend-точки

`interface-lab/server/selection_status.py` — небольшая читающая проекция:

| Источник | Что используем |
|---|---|
| `selection.py` / product SQLite | candidate ID, вакансия, версия профиля, контакты, согласования, квитанции доставки |
| `GET /v1/candidates/{candidate_id}/dossier` | Все связанные интервью/встречи и метаданные материалов из существующего Core |
| `GET /v1/owners/{kind}/{id}/primary-transcripts` | Только выбранные тексты и состояние их выбора |
| `assessment_jobs.read_candidate` | Проверка актуальной ревизии существующей аналитики; не запуск нового ядра |
| `GET /v1/assessments/{run_id}` нового ядра | Следующий источник оценки после подключения авторизованного адаптера |

Новый frontend endpoint:

```text
GET /api/hr/selection/candidates/{candidateId}/readiness?vacancyId={vacancyId}
```

Он требует внутреннюю manager-сессию, проверяет существование кандидата и
вакансии, снимает общий application lock перед сетевыми чтениями, затем
повторно проверяет доступ и локальную sourceRevision. Ответ — `no-store`.
Чужой candidate ID в ответе Core отклоняется. Браузер не получает service token,
полный текст расшифровки, provider URL или право читать SQL.

Readiness возвращает `{candidateId, materials, assessment}`. Материалы — числа
записей/выбранных текстов и состояния по владельцам. При недоступности Core
числа равны `null`, а не нулю. Состояние ready означает наличие выбранного текста;
**оно не является приёмкой полноты корпуса для модели**. Будущая встреча без
материалов не отменяет наличие текста прошедшего интервью.

Существующий dossier отдаёт только метаданные CV. `cp_resumes.text_content`
нужно читать через авторизованный адаптер владельца данных. Новый сборщик,
PDF-парсер, ASR или выбор основной расшифровки здесь не создаются.

## Принятый формат нового ядра

Прочитан реализованный `services/assessment-core/API.md` из рабочего проекта
«Ядро»: **`full-corpus-level-choice-v1`**. Код пока локальный; рабочие шкалы и
подключение базы ещё не приняты.

Подготовлен общий компонент
`src/scenes/interview-assessment/FullCorpusAssessment.tsx`. Он принимает
сохранённый `FullCorpusRun` непосредственно в формате нового API:

- состояния queued/sent/response_saved/completed/failed/outcome_unknown;
- для каждого параметра — собственные labels/описания уровней,
  selected_level_id и все probabilities;
- insufficient_data отдельно от уровней, confidence отдельно от вероятностей;
- версии корпуса/шкалы, ID расчёта и состав источников.

Компонент не переводит это в старый `candidate_profile/1`, не извлекает число из
`L3`, не перенормирует вероятности и не придумывает цитат. При несовпадении
candidate ID, run ID, corpus hash, rubric version или версии контракта результат
не отображается. `outcome_unknown` не имеет автоматической кнопки повтора.

В readiness зарезервировано `assessment.coreRun`. Локальный preview подставляет
синтетический сохранённый ответ нового ядра; **боевой endpoint пока не возвращает
coreRun**. Существующее поле `assessment.result` остаётся для текущей аналитики.
При наличии coreRun UI не показывает одновременно старые критерии и сравнение.

## Следующий шаг интеграции после готовности ядра

1. Принять рабочие собственные шкалы и контракт авторизованного корпуса.
   Сверить CV + ожидаемые интервью и все части записей; не включать автоматически
   любые встречи из dossier. Один primary.status=ready недостаточен для полноты.
2. Сервер сохраняет связь candidate ID → corpus revision + rubric revision →
   run ID. Явный запуск/продуктовое событие отправляет POST нового API. GET
   карточки только читает результат; никакого скрытого перерасчёта.
3. Перед выдачей coreRun сверять доступ и текущую ревизию всего корпуса и шкалы.
   Передать исходный ответ без пересчёта вероятностей. Одинаковую ревизию
   подключить к операторской таблице и существующей публичной карточке.
4. Формулу сопоставления и веса вакансии принять отдельно. Нельзя объявить
   completed оценку навыков основанием для canAdd. Разрешение отправки приходит
   от проверенного актуального результата сопоставления.
5. Пройти семь реальных профилей: Айгерим, Виталий Багин, Елена Рыбкина,
   Степан Ушеренко, Евгений Керимов (две части), Николай Шкунов, Роман Исмагилов.
   Проверить отсутствие дублей, состав корпуса, одну ревизию во всех экранах,
   stale после замены текста, отсутствие новых вызовов при чтении.
6. Явное добавление проходит существующие nominations/outbox/согласие. Просмотр
   подборки не рассылает уведомления. Приёмку доставки выполнять на согласованных
   тестовых аккаунтах, не выдавать HTTP 200 за доставку адресату.

## Проверки и выкладка

`npm run typecheck`, service build; отдельно package-release/receiver allowlist.
Синтетический preview и логи в `output/playwright/selection-core-readiness/`.

нужно обновить receiver штатным путём. В этом изменении remote receiver, БД,
конфигурация сервисов и production не менялись.

Полный локальный receiver suite упёрся в минимальный запас диска; guard не
отключался. Целевые проверки комплектности архива прошли. Это ограничение
окружения не заменяет production preflight и сквозную приёмку семи кандидатов.
