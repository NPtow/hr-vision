# Встречи и обратная связь после интервью в HR Vision

Проверено 04.10.2026. Исследование через Context7 (`search`, затем `docs`) и текущие первичные источники. Сервер и облако не изменялись. Это рекомендация и контракт интеграции для согласования, не утверждение, что видеосервис уже запущен. Уточнение Никиты: речь об обратной связи **после интервью** и оценке интервью, как в существующей панели. Ранее описанная отдельная видеозапись объяснения отказа исключена из объёма работ.

## Решение

**Рекомендуем LiveKit для встреч внутри нашего приложения.** Для первой поставки подходят готовые React-компоненты с нашей оболочкой; минимальная комната содержит камеру, микрофон, демонстрацию экрана и завершение встречи. Jitsi остаётся запасным вариантом, если приоритетом станет готовый полноценный Zoom внутри iframe. Выбор согласуется до реализации.

Причина выбора: пользователь хочет единый путь «подборка → встреча → обязательное ревью → оценка → оффер». LiveKit даёт управляемые React-компоненты и серверные события; внешний вид и переходы принадлежат HR Vision. Это инженерный вывод из API, а не обещание готовности сервиса. [React components](https://github.com/livekit/components-js), [VideoConference](https://docs.livekit.io/reference/components/react/component/videoconference/).

| Вопрос | LiveKit | Jitsi Meet |
|---|---|---|
| Готовая комната | `LiveKitRoom`, `PreJoin`, `VideoConference`; можно постепенно заменить UI своими компонентами | React SDK оборачивает готовую конференцию в iframe; самый короткий путь к знакомому Zoom |
| Наш дизайн | Компоненты и hooks внутри нашего DOM | Ограниченная настройка iframe; полная переделка требует более низкого уровня `lib-jitsi-meet` |
| Авторизация | Сервер выдаёт JWT для конкретных identity и room | JWT/secure domain на собственном Jitsi, JWT передаётся SDK |
| Выход из комнаты | `onDisconnected` сообщает о клиенте; серверные webhooks дают состояние комнаты | `videoConferenceLeft` сообщает о выходе локального пользователя; `readyToClose` означает готовность закрыть iframe |
| Запись | Egress, отдельный сервис при self-host; MP4/HLS или отдельные дорожки | Jibri: отдельная машина/VM, один процесс записывает одну встречу; требует полного Jitsi Meet |
| Ресурсы | SFU ограничен CPU/сетью; Egress рекомендует минимум 4 CPU/4 GB на worker | Помимо JVB/Prosody/Jicofo, запись запускает Chrome + ffmpeg в Jibri |

Источники: [Jitsi React SDK](https://jitsi.github.io/handbook/docs/dev-guide/dev-guide-react-sdk/), [JWT](https://jitsi.github.io/handbook/docs/devops-guide/token-authentication/), [Jitsi events](https://jitsi.github.io/handbook/docs/dev-guide/dev-guide-iframe-events/), [Jibri](https://github.com/jitsi/jibri), [LiveKit deployment](https://docs.livekit.io/transport/self-hosting/deployment/), [Egress](https://docs.livekit.io/transport/self-hosting/egress/).

## Как работает путь пользователя

1. После назначения встречи в конкретной подборке появляется карточка «Встреча с …». До назначения раздела встреч нет.
2. Перед входом: имя кандидата, задача найма, проверка микрофона/камеры, понятное уведомление о записи и её назначении. Одна основная кнопка «Войти на встречу».
3. В комнате: видео, минимальная панель управления, «Завершить встречу». Никаких резюме и оценочных таблиц поверх разговора.
4. После подтверждённого завершения открывается отдельный обязательный короткий отзыв менеджера. Состояние сохраняется на сервере; при повторном входе незавершённый отзыв остаётся следующим шагом. До его отправки не показываем машинную оценку, чтобы она не подсказывала ответ.
5. После отзыва: «Готовим разбор интервью», затем оценка с доказательствами. Ошибка записи или обработки показывается явно; фиктивного результата нет.

Это продуктовый контракт по запросу Никиты. Методология вопросов и оценки описывается отдельным исследованием.

## События и серверный контракт

Клиентский disconnect **не доказывает**, что интервью состоялось или завершилось. У LiveKit `room_finished` означает закрытие комнаты, включая истечение timeout после ухода последнего участника; доставка webhook повторяется, но не гарантируется. [Webhooks](https://docs.livekit.io/intro/basics/rooms-participants-tracks/webhooks-events/).

Рекомендуемая модель:

```text
scheduled → live → ending → feedback_required → processing → assessment_ready
                  ↘ interrupted / no_show
```

- `POST /api/meetings/:id/join`: аутентификация, принадлежность к компании/приглашению, проверка участника и статуса встречи. Клиент передаёт только meetingId; room, identity, grants вычисляет сервер. Ответ `{ serverUrl, participantToken }`.
- `POST /api/meetings/:id/finish`: право ведущего, optimistic lock/идемпотентность, статус `ending`, завершение комнаты через provider API; затем подтверждение результата. Выход кандидата не завершает встречу за менеджера.
- `POST /api/webhooks/livekit`: raw body + проверка подписи `WebhookReceiver`, уникальный `event.id`, durable event inbox. `room_started`/`participant_joined` фиксируют присутствие, `room_finished` завершает RTC-сеанс, `egress_ended` обрабатывает отдельный результат записи.
- Встреча без участия обеих сторон не превращается автоматически в `feedback_required`. После технического обрыва предлагаем вернуться или подтвердить, что разговор завершён. Фоновая сверка room/egress API нужна на случай потерянного webhook.
- `POST /api/meetings/:id/feedback`: короткий обязательный отзыв, версия вопросника, временная метка, автор; только после сохранения запускается оценка. Не смешивать внутреннюю оценку с обратной связью кандидату.
- Запись: `pending → recording → uploading → ready | failed`. `egress_ended` сам по себе не означает успех: проверяем статус задания и наличие доступного объекта. Ключ объекта принадлежит tenant/meeting, доступ выдаётся после проверки прав.

## Готовая основа интеграции

Сейчас в проекте React 19.3.0. Проверенные версии npm на 04.10.2026: `@livekit/components-react@2.9.24` (React >=18), `@livekit/components-styles@1.2.0`, `livekit-client@2.22.3`, `livekit-server-sdk@2.19.1`; альтернатива `@jitsi/react-sdk@1.4.4` (React 16–19). Перед установкой фиксируем lockfile и проверяем типы. Команды проверки: `npm view <package> version peerDependencies --json`.

Серверная функция ниже готовит токен **после** нашей проверки доступа. `authorized` нельзя создавать из тела запроса без проверки. Не передаём `roomAdmin` или `roomRecord` в браузер. [Access tokens](https://docs.livekit.io/frontends/reference/tokens-grants/).

```ts
import { AccessToken } from 'livekit-server-sdk';

type AuthorizedMeeting = {
  providerRoom: string;
  participantIdentity: string;
  participantName: string;
};

export async function issueMeetingToken(authorized: AuthorizedMeeting) {
  const token = new AccessToken(
    process.env.LIVEKIT_API_KEY!,
    process.env.LIVEKIT_API_SECRET!,
    {
      identity: authorized.participantIdentity,
      name: authorized.participantName,
      ttl: '5m',
    },
  );
  token.addGrant({
    roomJoin: true,
    room: authorized.providerRoom,
    canPublish: true,
    canSubscribe: true,
    canPublishData: false,
  });
  return {
    serverUrl: process.env.LIVEKIT_URL!,
    participantToken: await token.toJwt(),
  };
}
```

Короткий TTL ограничивает первоначальное подключение, не длительность разговора. У self-hosted LiveKit удаление участника **не отзывает выданный JWT**. Не обещаем мгновенного отзыва: прекращаем выдачу новых токенов, используем уникальную комнату для каждого сеанса и короткий TTL. Для строгого отзыва требуется дополнительное решение; в LiveKit Cloud эта возможность есть с отдельными условиями. [Token lifecycle](https://docs.livekit.io/frontends/reference/tokens-grants/#token-lifecycle).

Минимальная клиентская интеграция, без притворного завершения:

```tsx
import { LiveKitRoom, VideoConference } from '@livekit/components-react';
import '@livekit/components-styles';

export function InterviewRoom(props: {
  credentials: { serverUrl: string; participantToken: string };
  onConnectionLost: () => void;
  onError: (error: Error) => void;
}) {
  return (
    <LiveKitRoom
      serverUrl={props.credentials.serverUrl}
      token={props.credentials.participantToken}
      connect
      video
      audio
      onDisconnected={props.onConnectionLost}
      onError={props.onError}
      data-lk-theme="default"
      style={{ height: '100dvh' }}
    >
      <VideoConference />
    </LiveKitRoom>
  );
}
```

Это стартовый готовый видеокомпонент, а не финальный минимальный UI. `onConnectionLost` сверяет статус встречи на нашем backend; переход к отзыву разрешён только при подтверждённом завершении. Кнопку завершения ведущим подключаем к `/finish`. После PreJoin передаём выбор устройств/мьюта вместо принудительного `video/audio`.

## Граница обратной связи

После проведённой встречи менеджер заполняет обязательный отзыв; далее получает оценку интервью с подтверждающими фрагментами записи, если запись существует. Это продолжение разговора в той же задаче найма. Отдельный сценарий записи видеообъяснения отказа и endpoints `feedback-videos` не входят в актуальное предложение. Получатель и правила публикации отзыва кандидату отдельно здесь не определяются.

## Что можно реализовать сейчас и что требуется запустить

**Кандидаты на реализацию после согласования:** адаптер провайдера, UI предвхода/комнаты/ошибок, серверные join/finish/webhook handlers, сохранение записи встречи и переход к обязательному отзыву, тесты на обрыв/повторный webhook/чужую встречу. Это не требует сочинять готовые записи или результаты интервью. В рамках этого исследования код не изменялся.

**Для реальной работы:** доступный LiveKit URL и ключи только на сервере; HTTPS и TURN/TLS для корпоративных сетей; Egress, Redis и приватный object storage; текущая серверная auth/DB, очередь обработки и worker. До настройки `/join` честно возвращает недоступность сервиса, кнопка не открывает публичный `meet.jit.si` и не изображает живого собеседника.

Для self-host в YC рекомендуем отдельный узел SFU и отдельный recording worker. 4 CPU/4 GB в документации относятся к Egress, не являются гарантией вместимости всей системы. Ёмкость SFU проверяется нагрузочным тестом и сетью. На общий сервер, у которого по последней проверке родительского агента заполнен диск, новые медиасервисы не добавлять до устранения инцидента. Альтернатива для быстрого запуска реальных разговоров: LiveKit Cloud с тем же UI/API, после выбора аккаунта, региона и условий хранения. [Deployment](https://docs.livekit.io/transport/self-hosting/deployment/), [Egress](https://docs.livekit.io/transport/self-hosting/egress/).

Минимальная проверка перед объявлением запуска: два разных авторизованных браузера слышат и видят друг друга; чужой пользователь не входит; отказ камеры и потеря сети корректно обрабатываются; запись реально воспроизводится; duplicate webhook не создаёт вторую оценку; после завершения открывается отзыв; без отзыва оценка не запускается; reload восстанавливает серверный статус.
