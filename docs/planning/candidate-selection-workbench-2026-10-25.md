# Таблица подбора

Операторский вход: существующая история `hr-vision-product--manager`, параметр
`workspace=selection`. Доступ — только команда; личная сессия работодателя или
рекрутера не открывает общую базу. Кнопка «Подборки» находится в рассылке HH.

## Референсы

- NocoDB Grid: компактная таблица, поиск, редактирование значения на месте.
  https://nocodb.com/docs/product/tables/views/view-types/grid
- Attio: отметить строки, выбрать целевой список, добавить одним действием.
  https://attio.com/help/reference/imports-exports/moving-records-between-lists
- Directus: связь многие-ко-многим через отдельную связующую таблицу.
  https://directus.com/docs/guides/data-model/relationships

Используем эти механики в существующем МашаДаша_UI. Не устанавливаем отдельную
CRM или прямое подключение браузера к SQL. Код таблицы не считает оценки.

## Классический путь

1. `cp_candidates` + `cp_interviews`: исходный человек, резюме и интервью.
2. Ядро из «Верстак (2)» возвращает `candidate_profile/1` с отдельными критериями.
   `unknown`, `not_applicable`, `failed_processing` сохраняют собственный смысл.
3. Подтверждённые требования реальной вакансии + `match/1` дают рекомендацию.
   Числовой общий балл не придумываем. Пока сопоставления нет — добавление закрыто.
4. Оператор отмечает рекомендованных людей и создаёт номинации (`sl_nominations`).
   У подготовленного профиля ещё нет аккаунта: приглашение ведёт в существующий
   `cp=claim`. Активный аккаунт получает обычный вход. Обе доставки используют
   существующий durable outbox и штатный worker, отдельный отправитель не создаётся.
5. Источники контактов — аккаунт либо адрес/чат, оставленные при записи на интервью.
   Контакты из резюме автоматически не присваиваются. Если канала нет, таблица
   показывает это; отправку не объявляем успешной.
6. После активации и согласия на использование интервью номинация проходит через
   `employer_store.import_batch` и штатное предложение вакансии. Решение кандидата
   о конкретной вакансии остаётся отдельным. Только accepted + consentReuse
   делает профиль доступным работодателю. Отправка не равна просмотру письма.

## Контракт ядра / агента

Все методы `/api/hr/selection/*` требуют существующую внутреннюю manager-сессию.
Данные, ключи и связи работодателей остаются на сервере.

- GET `vacancies`: фактические вакансии и `contentHash`.
- GET `candidates?vacancyId=...`: таблица, `sourceRevision`, результаты и состояния.
- POST `candidates/update`: candidateId, revision, fields (name, desiredRole,
  city, about). CAS и журнал; пароль, почта аккаунта и согласия не редактируются.
- POST `cohort`: vacancyId, candidateIds — рабочая группа для просмотра, без отправки.
- POST `results`: candidateId, interviewId, engineCandidateId, jobId, requestHash,
  sourceRevision, document (`candidate_profile/1`). Проверяются владелец, реальная
  модель, seal документа, состояние критериев, актуальность источника. Идемпотентно.
- POST `requirements`: vacancyId, vacancyHash, engineVacancyId, document
  (`requirement_profile/1`, state=confirmed). Не подтверждает требования за человека.
- POST `matches`: resultId, requirementId, document (`match/1`), rank. Проверяются
  точные ссылки и hashes профиля/требований. Рекомендацию определяет partition ядра.
- POST `publish`: vacancyId, candidateIds, requestId. Вся группа валидируется
  перед записью. Повтор с тем же запросом возвращает квитанцию, сообщений не дублирует.

`scripts/selection-import.py` переносит уже полученные результаты через этот API.
Модель не вызывается; корпус и результаты не входят в публичную сборку.
Материалы, критерии и подборки не заменяются демонстрационными данными при ошибке.

## Проверка / границы

В текущих результатах трёх интервью по 7 unknown и 8 not_applicable. Это не
положительная рекомендация и не основание для рассылки. У четырёх файлов с Диска
пока нет результата этого ядра. Подготовка интерфейса не превращает их в оценённых.
Никакие кандидатские согласия оператором не включаются.
