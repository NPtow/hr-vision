# Уведомления о встречах

Утверждённый каталог: первичная запись, предложение времени, подтверждение,
напоминания за 24 часа и 15 минут, запрос обратной связи после завершения.
Реализация использует один существующий worker и SMTP/Telegram transport.
Наличие строки `delivered` означает приём провайдером; фактическое получение
человеком проверяется отдельно.

| Тип | Канонический hook | Получатели / каналы | Действие |
| --- | --- | --- | --- |
| 1. Первичное интервью назначено | `CandidatePortal.book` → существующие `interview.booked`; для booking-only — существующий `booking.confirmed` | Кандидат: email с подтверждённым адресом + связанный Telegram. Booking-only: согласованный контакт и отдельная `bk_` привязка. Назначенный рекрутер: email аккаунта + его Telegram | Кандидат: своё интервью; booking-only: та же персональная ссылка; рекрутер: существующий личный кабинет |
| 2. Работодатель предлагает время | `propose_meeting` → существующий `meeting.proposed` | Кандидат, оба независимо доступных канала | Точная заявка с действием «Подтвердить время» |
| 3. Кандидат подтверждает | `confirm_meeting` → существующий `meeting.confirmed` | Кандидат и активный личный аккаунт работодателя канонического workspace, каждый по email и Telegram | Кандидат: точная заявка/встреча; работодатель: точный этап встречи |
| 4. За 24 часа | Существующий `meeting_reminders.collect`, `offset=86400` | Кандидат + назначенный рекрутер для первичной встречи; кандидат + работодатель для встречи работодателя; оба канала | Существующие действия перехода к встрече |
| 5. За 15 минут | Тот же scheduler, `offset=900` | Те же участники и каналы | Кнопка встречи; booking-only сохраняет ограниченную персональную ссылку |
| 6. Встреча работодателя завершена | `_complete_room`: успешное изменение `live → completed` → новый `meeting.completed` | Кандидат и личный работодатель, оба независимо доступных канала | Кандидат: существующий ответ «Хочу продолжить / Не продолжать» в заявке. Работодатель: существующая форма обратной связи на точном этапе встречи |

Для Telegram работодателя кнопка использует `web_app` со входом через проверенный
Telegram initData и существующей привязкой. Email ведёт на обычный сайт без
параметра `miniapp`; требуется существующая авторизованная сессия. Кандидатские
ссылки сохраняют `cp`, `application`, `meeting` при переходе на вход и перезагрузке
страницы входа. `returnCp` допускает только внутренние страницы кабинета; он не
выдаёт доступ к чужим данным и не принимает внешние URL или booking capabilities.

## Транзакции и актуальность

Новый `meeting_notifications.py` добавляет контекст к прежним ключам событий
#1/#2/#3 в `cn_outbox`, не создавая второй кандидатской отправки. Работодатель
использует изолированный owner `employer:<accountId>`. Новый #6 создаётся только
после фактического завершения комнаты, в транзакции изменения статуса встречи.
Запросы провайдерам остаются за пределами этой транзакции. Повторные confirm/complete
не создают новых событий; уникальность outbox сохраняется по owner/event/channel.

Новые события не собираются из истории и не добавляются на старте worker, при
подключении канала или при входе. Старые события без lifecycle snapshot сохраняют
прежний контракт. Встречи legacy team-only портала продолжают существующую
кандидатскую отправку; личность работодателя для них не выдумывается.

В момент claim сравниваются снимок встречи, время, ревизия, текущий статус,
владелец заявки/workspace, актуальная email/TG привязка. Предложение после начала,
подтверждение после конца, завершённая/заменённая встреча для старого приглашения,
архивная/отклонённая заявка или остановленный поиск не отправляются. Запрос
обратной связи не отправляется соответствующей стороне после её ответа;
кандидату — также при уже отправленном/принятом оффере. Отсутствующий канал
остаётся `disabled`, `unbound` или `unverified`, а не «доставлен». Отдельный канал
не блокирует другой. Известные временные сбои используют существующий bounded
retry; неопределённый исход — quarantine. Ручной retry lifecycle notice не
переводит terminal rows обратно в pending и не меняет получателя.

Напоминания #4/#5 не изменены: две независимые доставки каждому участнику,
окно catch-up 10 минут, пропуск порогов, наступивших до создания/подтверждения,
проверка текущего состояния и запрет повторного воспроизведения.

## Выпуск и проверка

Перед выпуском установить reviewed receiver: новый полный runtime включает
`meeting_notifications.py`. `PRE_MEETING_NOTICES_RUNTIME` сохраняет предыдущий
полный layout с `meeting_reminders.py`; все более старые layouts также сохранены.
Новых таблиц, env, worker, cron, provider-клиентов или миграции данных не требуется.

Принятый архив не означает безопасный откат данных. Перед каждым переключением
API receiver останавливает unit с HTTP и worker, затем под SQLite write lock
проверяет совместимость outbox и меняет указатель. Любая lifecycle-строка
(включая terminal) или `meeting.completed` запрещает запуск прежнего runtime
без `meeting_notifications.py`. Это защищает и повторно используемые события
от потери snapshot-проверок, и completion retry от `KeyError` старого dispatcher.
Проверка повторяется при автоматическом fallback после неуспешного health check.
При отказе fallback API остаётся остановленным после успешного stop; данные
сохраняются без удаления, replay или изменения получателя. Требуется совместимое
forward recovery. Обычные прежние строки допускают прежний layout; совместимый
runtime допускает lifecycle-строки. Недоступная/занятая база или некорректные
данные не разрешают старый runtime. [Подробный порядок восстановления](../infra/deployment/web/ci/README.md#откат-после-выпуска-lifecycle-уведомлений).

Изолированные проверки: `test_meeting_notifications`, прежние candidate/recruiter/
employer notification и reminder suites, canonical portal/employer HTTP suites,
booking-only/bot suites; `scripts/candidate-navigation.test.ts`; receiver tests.
SMTP и Telegram в этих проверках подменены; production и фактическое получение
уведомлений этими тестами не подтверждаются.
